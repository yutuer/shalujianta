校验器（`tools/check-task-stats.ps1`）要靠正则读 markdown 表格，有两处必须注意，否则会出现"文档明明对，脚本却报漂移"：

## 1. 文档与代码会失同步

**（本项目最大的坑）** 真实发生过的失真，**改任何状态类表格都要同步**：

| 文档 | 失真表现 |
|---|---|
| `tasks.md` 统计表 | 自称 61 任务 / 23 完成，实际 87 行 / 33 完成（写完商店那轮 Sprint 后没回头更新） |


## 2. `.tscn` 是布局的唯一真相

`SilverKeyProgressIndicator.cs` 找 `ValueLabel` / `MaxLabel`，但 `.tscn` 里它们嵌在 `VBoxContainer` 下 → 每次进地图报 2 次 `Node not found`，而且**银钥圈里的数字从来没显示过**。

`HexMapUI.cs` 连 `SceneTree.screen_resized` —— **Godot 4 已移除该信号**，应为 `Viewport.SizeChanged`。

**教训**：`GetNode` 路径必须和 `.tscn` 实际层级一致；用 `GetNodeOrNull` 让缺失降级为警告而不是错误堆栈。跨 Godot 版本迁移时重点查信号名。

## 3. C# ↔ GDScript 桥接限制

调试时会撞墙的三条：

- C# 属性不加 `[Export]` → **GDScript 读不到**（`get("CurrentMap")` 返回 null）
- C# 的 public 方法 → **GDScript 也调不到**（`call("GetSavedMap")` 报 `Nonexistent function`）
- `.tscn` 里 Control 的位置存的是 `offset_left/offset_top`，不是 `position`

**教训**：跨语言调试要么写 C# 侧代码，要么改用 Godot 原生 API（`Label.text`、`Control.mouse_filter`、`Node.is_processing_input` 等）去观察。

## 4. 无头 / 后台窗口里模拟点击不可靠

godot-runtime MCP 的 `run_project(background: true)` 把窗口放在**屏幕外 `(-9999,-9999)`**，`Control.GetLocalMousePosition()` 读的是**真实 OS 光标**位置，合成事件改不了它 → 任何"点击命中某控件"的代码路径都测不到。

`HexTileView` 正是用 `GetLocalMousePosition()` 判断点击是否落在格子内。

**可行的替代**：写一个**临时 C# 集成测试**（临时注册成 autoload 以跨场景存活），由 C# 直接调游戏自己的 API 驱动流程，断言结果写进 `user://` 文件；测完把 autoload 注册和测试文件一并删掉。2026-10-20 用这招跑通了 24 项断言。

## 5. `git push` 会上传大文件

push 传输的是「**远端缺失的对象**」，不是增量 diff。若某个待推送提交引入了大文件而远端还没有，push 会真把那些 blob 传上去（实测 2.4GB 传了 4 分钟还没完），**哪怕下一个提交就删了它们**。

**正确做法**：先改写**从未推送过的**本地历史再推：

```powershell
git filter-repo --force --path <路径> --invert-paths --refs <远端SHA>..HEAD
```

只改写远端没有的提交，**不影响已推送历史，无需 force push**。

配套：改写后要清掉 IDE 留的记账引用（Trae 的 `refs/trae_merge/*`，用 `git update-ref -d <ref>`），再 `git reflog expire --expire=now --all` + `git gc --prune=now` 才会真正回收磁盘空间。

**现在怎么做**：导出产物（`dabao/`、`qianye.*`、`*.tpz`、`*.rar`）、`.godot/`、`.mcp/`、原始参考图 PNG 都已在 `.gitignore` 里；参考图入库前先压到 3.2MB 再推。

- `winget install GitHub.cli` → `0x8007029c`（安装器断言失败）
- 官方 MSI 静默安装 → `msiexec` 返回 **1603**
- ✅ **便携版 ZIP 直接解压即可**，放到 `C:\Users\yutue\Tools\gh\bin` 并加进用户 PATH
- `git-filter-repo` 用 `pip install`（脚本装到 `%APPDATA%\Python\Python314\Scripts`，同样要加 PATH）
- **PowerShell 里 `\"` 不能转义双引号**（要用反引号），`git commit -m "含 \" 引号\""` 会被拆成多个参数 → **多行提交信息一律用 `git commit -F 文件`**
- 某些 shell 会话的 PATH 里**没有 `gh`**（用户级 PATH 变更未继承到该进程）→ 用绝对路径 `C:\Users\yutue\Tools\gh\bin\gh.exe`

## 8. `.tscn` 根节点漏绑 script → 组件静默退化成空节点

2026-10-20 在战斗场景排查报错时发现：`AttackerDisplayUI.tscn`、`RageDisplayUI.tscn`、`KeyOrderSelectionUI.tscn` **三个场景的根节点都没有 `script = ExtResource(...)`**（ext_resource 声明了脚本，但没挂到根节点上）。

后果很隐蔽：`BattleManager.LoadUIComponent<T>()` 里的 `packedScene.Instantiate<T>()` 因为类型不匹配返回 null，于是走**代码兜底** `new T()` —— 得到一个**没有任何子节点的空 Control**。于是运行日志里出现：

```
[BattleManager] 攻击体角色显示UI初始化成功      ← 看着像成功
ERROR: Node not found: "VBoxContainer/TeamStatsLabel"   ← 其实是空节点
```

**攻击体编队、怒气槽、钥令选择这三个 UI 实际上一直是空的**，只是没有崩所以没人发现。修法就是在根节点补一行 `script = ExtResource("1")`。

**教训**：

- 新建 `.tscn` 时，**根节点一定要绑脚本** —— 只声明 ext_resource 不等于挂上了
- 「从场景加载: xxx.tscn」这条日志是组件是否真的走了场景路径的判据；缺它就说明退回了代码兜底
- 一键排查：`Scenes/**/*.tscn` 里凡是有 Script ext_resource 的，根节点都要有 `script =`

## 10. 子节点也要挂脚本，且一个 .cs 只能一个类

接 §8：修好根节点的 script 之后，`AttackerDisplayUI` / `RageDisplayUI` 虽然能加载了，但它们的 **4 个槽位节点（`CharacterSlot0..3` / `RageSlot0..3`）还是空 Panel**，日志报「未找到角色槽位节点」。原因有两层：

1. 槽位节点也没挂脚本 → `GetNode<Panel>(path) as CharacterSlotUI` 得到 null
2. **`CharacterSlotUI` / `RageSlotUI` 原本和宿主类写在同一个 .cs 文件里**（Godot 一个脚本文件只能对应一个类，`.tscn` 挂脚本时按文件绑定），必须先拆成 `Scripts/UI/CharacterSlotUI.cs` / `Scripts/UI/RageSlotUI.cs` 再挂

**教训**：新建带子组件的 UI 场景时，**每个需要脚本的节点都要单独挂脚本，且对应独立的 .cs 文件**；写完用 `HasNode(path)` 验证过的路径去取，取不到时 Godot 只报「未找到」不崩，很容易被忽略。

## 13. PowerShell 脚本的 UTF-8 BOM

**（2026-10-20）** 用文件写入工具新建 `.ps1` 通常写成**无 BOM**，PowerShell 5.1 读它时把中文当 ANSI 解析成乱码。

关键在于**乱码会连累参数解析**，报出的错误完全看不出是编码问题：

```
A positional parameter cannot be found that accepts argument '*.png -File | Sort-Object Name'
```

这个报错看起来像脚本逻辑写错，实际是编码问题。**排查顺序**：先查文件头三字节是不是 `239,187,191`（UTF-8 BOM），再怀疑逻辑。

补 BOM 的做法（不依赖编辑器）：

```powershell
$p = 'tools\convert-reference-images.ps1'
$txt = [System.IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($p, $txt, (New-Object Text.UTF8Encoding $true))
```

**用编辑工具改已有的 .ps1 一般不会丢 BOM**（BOM 在文件首字节，替换的是中段内容），但**新建文件会**。改完一律用首三字节核对，别等跑报错。

## 17. 术语/结论会随模型演进而过期

本项目的地图模型在一天内被推翻了三次（「簇只由洞产生」→「簇有两个来源」；「三层结构」→「四层」；
「洞 = 桥」→ 洞是**顶点**、要判断的是**割点**）。**文档里的术语一旦落后于模型，读者就会按错的模型理解代码。**

2026-10-20 的回读测试抓出三类问题：

| 类型 | 例子 | 修法 |
|---|---|---|
| **术语错误** | 把「洞」写成「桥（cut edge）」—— 洞是格子（顶点），消耗后消失，要判断的是**割点（articulation point）** | 术语写错比不写更危险，直接改 |
| **旧称残留** | 「桥树」与引入传送门/单向门后的「簇图」混用 | 统一改称；旧称只允许出现在**术语纠正段**里做对照 |
| **结论过期** | 早期条目说「簇只由洞消耗产生」 | 变更记录表**上方加「以最新条目为准」说明**，并列出被推翻的结论 |

**教训**
- 早期条目不是垃圾，是**当时的真实结论**；但必须标注它已被修正，否则会被误读成现状
- 回读测试要**固化成脚本**，不能靠人记得做 → `tools/check-doc-consistency.ps1`

**顺带一个 PowerShell 坑**：`[System.IO.File]::WriteAllLines()` 在 Windows 上默认写 **CRLF**，
会把原本 LF 的文件整体转成 CRLF——之后 `edit` 工具的所有多行匹配全部失败（LF 与 CRLF 不匹配），
排查方向容易跑偏。用 `WriteAllText()` 保留原换行，或写完统一 `Replace("`r`n","`n")`。

## 19. 「地图完成」这个状态没有落到数据层

六边形地图模式下，地图完成的链路是：

```
BattleTransitionManager.PendingMapCompletion（标记）
  → 回地图 → HexMapController.RestoreMapState() 读到标记
  → 打印「BOSS 已击败，结算地图完成」→ CompleteMap()
  → 只发 OnMapCompleted 事件 + 清存档
```

问题：
- `MapManager.CompleteMap()`（设置 `_isMapCompleted`）**根本没被调用** → `MapManager.IsMapCompleted()` 在六边形地图模式下**恒为 false**
- `MapDefinition.IsCompleted` 也没被设置
- 也就是说：**「这张地图打完了」这个事实没有任何地方存着**

影响：以后要做「地图选择 / 关卡进度 / 存档」时，得先补一个可查询的完成状态。

**教训**：写「完成 / 失败」这类**状态**时，要明确它落在**哪个数据对象**上。
只有事件和日志是不够的 —— 事件会随场景一起销毁，测试也断言不了。

## 20. 文档标题里的状态标记必须放行尾

`tools/check-task-stats.ps1`（以及 `check-doc-consistency.ps1`）用这个正则定位「逐项展开」的章节标题：

```
^(###\s*(D\d+)\s*·.*?)(状态标记)\s*$
```

**状态标记必须是标题的最后一个东西**。写成这样会匹配失败：

```
### D4 · 战斗胜利结算界面 ✅ **已完成**     ← ❌ 标记在中间
```

必须写成：

```
### D4 · 战斗胜利结算界面 **已完成** ✅     ← ✅ 标记在行尾
```

报错信息是「开发计划条目 [D4] 在需求池总表有，但逐项展开缺对应标题」——
**看起来像标题写错了，其实是标记位置不对**，容易误判。

**教训**：写完条目标题，习惯性把状态标记放到最后；改完跑一次 `check-doc-consistency.ps1` 就能立刻发现。

（这个坑今天在 D4 和 D1 上各踩了一次，都是校验器当场报出来的。）

## 21. 一次性事件的类型，在触发回调之前就被清空了

D5 做探照灯时踩的。

`HexTile.Trigger()` 的流程是：**先**把 `EventType` 清成 `Empty`（一次性事件用完即焚），**再**发出 `OnTileTriggered` 回调。

所以在 `OnTileTriggered` 里读 `tile.EventType` 拿到的永远是 `Empty` —— 探照灯认不出来，弹窗不出现。

日志里能直接看到证据：

```
[HexMapUI] OnTileTriggered: tile=(-1, 2), EventType=Empty    ← 类型已经被清了
[HexMapUI] OnMapEventTriggered: searchlight @ (-1, 2)        ← 换个订阅点就对了
```

**修法**：改订阅 `HexEventManager.OnEventTriggered`（事件类型在**那一刻**还在），而不是格子层面的 `OnTileTriggered`。

**教训**：订阅格子事件时，先问一句「这个回调拿到的数据还是原始的吗」。
凡是「用完即焚」的状态（一次性事件、消耗型道具），**清理动作要放在回调之后**，否则订阅方永远看不到它。

## 22. 「存了但从来没被读过」= 死代码

D5 的 1.9.5「已照亮集合进地图存档并恢复」—— 我先写了存档端（`BattleTransitionManager.SaveRevealedTiles`），
以为「恢复」是自动的。直到写测试时才发现：**`RestoreRevealedTiles()` 这个方法全项目只有定义、没有任何调用点**。

也就是说存档写进去了，但**战斗返回地图时根本没人去读**，功能等于没做。

这跟 D8 发现的 `EffectRegistry.LoadFromJson()` 是同一类病：
**「写」的那半边很容易写完就以为完事了，「读」的那半边要单独确认。**

**修法**：
- 在 `RestoreMapState()`（战斗返回地图的唯一入口）里显式调用恢复
- 恢复时**校验关卡标识**，否则换关卡会继承上一关的视野
- 新地图生成（`GenerateMap()`）时清空存档

**教训**：写「持久化」这类需求时，**必须能说出「谁在什么时候读它」**。
写完把方法名 grep 一遍，确认有调用点；没有就是半成品。

## 23. 加公共 UI 之前，先查有没有既有的同类组件

## 24. 手写的 `uid://xxx` 不是 Godot 的合法 UID，每次加载都刷警告

在 `.tscn` 里手写场景引用时，我习惯给每个资源加一个「好认的」 uid：

```
[ext_resource type="PackedScene" uid="uid://scorepanel" path="res://Scenes/UI/ScorePanel.tscn" id="7_scorepanel"]
```

Godot 的 UID 是 **base31 编码**的短字符串（形如 `uid://dhynr33kc8wor`），
`scorepanel` 这种带小写明文的串**解不出来**，于是每次加载场景都会刷：

```
WARNING: res://Scenes/UI/HexMapUI.tscn:9 - ext_resource, invalid UID: uid://scorepanel
         - using text path instead: res://Scenes/UI/ScorePanel.tscn
```

功能上是没问题的（Godot 会退回用 path 匹配），但**每次启动都刷警告**，
真正出问题时警告就被淹没了。

**修法**：新写的 `.tscn` **不要手写 uid**，只写 `path`；
根节点的 `uid="uid://..."` 也一并去掉，让 Godot 自己在编辑器里保存时分配。

**教训**：Godot 资源文件里看起来「像格式」的自造值不一定合法。
手写配置时优先用**最朴素的合法形式**（path 而非 uid），让工具自己补全那些需要唯一标识的字段。

## 25. 「取不到就跳过」的写法，会把配置错误藏起来

D3 做关卡详情弹窗时，敌方预览和奖励预览的图标**一片空白**，但代码里没有任何报错。

原因是我在 slot 里这样取节点：

```csharp
_icon = GetNodeOrNull<TextureRect>("Icon");   // ← 实际路径是 "Frame/Icon"
```

`GetNodeOrNull` 取不到就返回 `null`，而我的代码是「取不到 → 隐藏图标」，于是**看起来像「资源不存在」**，
实际上是我把路径写错了 —— `Icon` 在 `Frame` 下面，不是 slot 的直接子节点。

同时还叠加了第二个错误：图标路径 `res://Assets/Icons/enemy.png` **这个文件根本不存在**
（项目里只有 `enemy_elite.svg` / `enemy_cultist.svg` / `skull.svg`）。

**两个错误叠在一起，表现完全一样：一片空白。**

**修法**
1. 路径改成 `Frame/Icon`
2. 敌人图标映射到**实际存在**的资源：BOSS → `skull.svg`、精英 → `enemy_elite.svg`、普通 → `enemy_cultist.svg`
3. 顺手把 `HexMapGenerator` 里指向不存在 png 的 9 个 `IconPath` 修了三个，
   并让 `HexTileView` 真正读 `IconPath`（文件不存在才回退到文字符号）

**教训**

- **`GetNodeOrNull` 返回 null 时，不要静默跳过** —— 至少打一条 `GD.PrintErr`，
  否则「我写错了路径」和「资源不存在」会被当成同一件事。
- **引用资源前先确认它存在**：`ResourceLoader.Exists(path)` 先判一次，
  或者写完路径后 glob 一遍资源目录确认文件名。
- **「界面空白」类的 bug，先怀疑路径，再怀疑资源，最后才怀疑渲染逻辑** —— 顺序反了会浪费很多时间。

## 26. 两个 Godot / C# 的语法与样式陷阱

D10 改关卡展示页时连踩两个，都不报错、只是「不生效」。

### 陷阱一：`?.Pressed += ...` 是 C# 14 特性

```csharp
_prevButton?.Pressed += () => SwitchChapter(-1);   // ← CS9202
```

「null 条件**赋值**」是 C# 14 才有的，项目是 C# 12 → 编译直接报错：

```
error CS9202: 功能"null 条件赋值"在 C# 12.0 中不可用。请使用语言版本 14.0 或更高版本。
```

**正确写法**：

```csharp
if (_prevButton != null) _prevButton.Pressed += () => SwitchChapter(-1);
```

> 注意区分：`?.Pressed`（读，安全）和 `?.Pressed +=`（赋值，C# 14）。
> 事件订阅一律用 `if` 判空。

### 陷阱二：PanelContainer 的内边距要配在 stylebox 上

想在卡片里留白，写成主题常量**不生效**：

```ini
theme_override_constants/content_margin_left = 18   # ← 无效，内容照样贴边
```

`PanelContainer` 的内容内边距来自 **panel stylebox 的 `content_margin_*`**，
要么改 StyleBoxFlat 的属性，要么用 `AddThemeStyleboxOverride` 在代码里设。

**正确写法**（写进 `.tscn` 的 sub_resource）：

```ini
[sub_resource type="StyleBoxFlat" id="StyleBoxFlat_card"]
content_margin_left = 18.0
content_margin_top = 12.0
content_margin_right = 18.0
content_margin_bottom = 12.0
```

**教训**：Godot 的「主题常量」和「样式里的属性」是两套东西，
**内边距/圆角/描边这类都住在 StyleBox 里**。
改样式没生效时，先确认改的是不是同一个地方 —— 跟 D3 的 `GetNodeOrNull` 路径问题一样，
**「静默不生效」比「报错」更难查**。

## 27. 弹窗每次打开都 `+=` 事件 → 点一次确认触发两次

D11 给商店加刷新二次确认时踩的。

最初的写法是**每次点「刷新」都订阅一次**：

```csharp
private void OnRefreshPressed()
{
    var dialog = GetOrCreateConfirmDialog();
    dialog.OnConfirm += DoRefresh;        // ← 每点一次刷新就多一个订阅者
    dialog.OnCancel += OnRefreshCancelled;
    dialog.ShowConfirm("确认刷新", "……");
}
```

看起来没问题（弹窗是复用的），但**事件不会自动清空**：
- 第 1 次点刷新 → 订阅 1 个 → 点「取消」，不触发刷新 ✓
- 第 2 次点刷新 → 订阅成 2 个 → 点「确认」→ `DoRefresh` 执行 **2 次** → **多扣一次黑印**

测试直接抓到了：断言「确认后刷新触发次数 == 1」，实际是 2。

**修法**：订阅放在**创建时**，不是每次显示时：

```csharp
_confirmDialog = _confirmDialogScene.Instantiate<ConfirmDialog>();
AddChild(_confirmDialog);
_confirmDialog.OnConfirm += DoRefresh;      // 只订阅这一次
_confirmDialog.OnCancel += OnRefreshCancelled;
```

**教训**

- **事件订阅要放在「生命周期开始」的位置**（创建 / `_Ready`），
  不要放在「每次显示」的位置 —— 后者会累积订阅者。
- 万一不得不重复订阅，就**先 `-=` 再 `+=`**。
- 这类 bug **不报错、只多点一次**，靠人眼点两下是发现不了的 ——
  **断言里要写死调用次数**（「触发次数 == 1」而不是「触发了」）。

顺带记一个同源的坑：**弹窗被下层内容盖住**。
光靠「后添加的节点画在上面」不总成立（地图格子的 `Line2D` 就盖过商店面板），
弹窗这类要显式设 `z_index`（`ShopUI` = 50，`ConfirmDialog` = 100）。

## 28. 主题里改尺寸 = 把既有布局挤爆

D2 做统一主题时踩的。

第一版 `MainTheme.tres` 里给按钮的 stylebox 设了内边距、还把默认字号调大：

```ini
content_margin_left = 18.0
content_margin_top = 8.0
...
default_font_size = 18
```

结果**关卡页右下角的两个按钮被挤出容器、叠在一起**（截图才看得出来）。

原因：Godot 容器（HBox / VBox）按子控件的**最小尺寸 + size_flags** 分配空间。
主题一旦改了控件的最小尺寸，**所有没重新算过的布局都会跟着变** ——
而项目里几十个 `.tscn` 的尺寸是各自手写的，没人算过主题的影响。

**修法：主题只负责「颜色与描边」，尺寸一律不管**

```ini
; 注意：这里**只定义颜色与边框**，不设 content_margin、不改 default_font_size ——
; 一旦改动控件尺寸，现有线框布局（按钮并排、HBox 排列）就会被挤爆。
```

改完立刻所有布局恢复原样，而底色/金线/字体色照样统一。

**教训**

- **Theme 优先只放「颜色 + 描边 + 字体」**，别碰 `content_margin` / `default_font_size` ——
  这两个是**尺寸**，会传导到所有容器的布局计算里。
- 真要统一尺寸，先在**一个**场景试，确认不炸再铺开。
- **改了主题必须截图看布局**，不能只看「主题加载成功」的断言 ——
  这次就是靠截图才发现按钮被挤爆的。

## 29. 测试用例的建模错误，会伪装成「算法有 bug」

D13 做地图校验器时，6 个断言挂了 —— 看起来像算法写错了。

**实际错的是测试用例本身**，三个坑叠在一起：

### 坑一：`End` 和 `required` 撞在同一个节点

```
节点 3 既是终点（End）又是必经格（required）
```

于是「访问到 required」就等于「到达终点」→ 死锁用例根本不成立，
状态空间正常返回 `CanComplete = true`，**算法被判死刑**。

### 坑二：`Normal` 表示「双向」，但用例只加了一个方向

玩具图里 `Connect(0, 1, Normal)` 只往邻接表里塞了 `0 → 1`。
可缩簇逻辑是按 `kind` 判断的 —— `Normal` 就算连接边 → `0` 和 `1` 被合并成一个簇。
**于是「簇」和「实际可达性」自相矛盾**，后面的判定全歪。

修法：`kind != OneWay` 时**自动补反向边**。

### 坑三：旁支用例把终点放在了旁支簇里

「拐进旁支就回不来」要成立的前提是**终点在起点那一侧**。
我把终点也放进了旁支簇 → 玩家拐进去照样能到终点 → **本来就不该报警**。

### 教训

- **写反向用例时，先用一句话说清「玩家在这里会怎样」，再动手画图。**
  图画完先自己走一遍（玩家从 S 出发能不能通关？required 在哪一侧？终点在哪一侧？）。
- **断言失败时，先怀疑用例，再怀疑实现** —— 尤其当多个用例同时失败、且失败模式很「整齐」时，
  通常是共用的建模假设错了，而不是算法错了。
- 调试手段：**把报告完整打出来**（`report.ToString()`）。
  D13 这次就是靠打印看出「簇 2、起点可达 4、能到终点 2」，
  立刻明白终点落在了旁支侧 —— 一眼看穿用例的错。

## 30. 「对」和「个」的口径不一致，配额永远差一倍

D14 做关卡配额时踩的。

规格里传送门写的是**「对数」**（`teleportOneWay: 1` = 1 对门），
但核对配额时我按**「格子数」**去比：

```
期望 1 个单向门格，实际 2 个   ← FAIL
```

原因：**每对传送门占 2 个格子**（入口 + 出口）。单向门、双向门都一样。

**修法**：把两个口径在代码里分开命名，不留模糊地带：

```csharp
/// <summary>单向门<strong>对数</strong>（每对占 2 个格子）</summary>
public int TeleportOneWay;

/// <summary>传送门占用的格子总数（每对 2 格）</summary>
public int TeleportTileCount => (TeleportOneWay + TeleportTwoWay) * 2;
```

配额核对、可满足性检查、测试断言三处全部改成用 `TeleportTileCount` 换算。

**教训**

- **配置里凡是「成对出现」的东西，都要明确写清楚单位**（对 / 个 / 格），
  并提供一个换算属性，别让每个调用点自己乘 2。
- **配额类数据最容易被「差一倍」坑到**：一个映射写反了，所有数量断言全错。
  写完先手算一遍最小的例子（1 对门 = 2 格）再往下写。

## 31. 「洞」在两处判定里的含义不一样，混用会导致永远判不出割点

D12 做洞消耗分裂时踩得最深的一个坑。

洞是**消耗型节点**，在两个地方含义完全不同：

| 场景 | 洞算不算连接边 | 问的是什么 |
|---|---|---|
| 判定「洞是不是割点」 | **算**（洞是普通可走格） | 洞**还在**的时候，它是不是连接两块的关键 |
| D13 的簇图分析 | **不算**（用掉即断） | 洞**已消耗**之后，地图还怎么连 |

我一开始用 D13 的 `ClusterGraphAnalyzer` 判割点，结果是：

```
洞候选 (6, 8) 不是割点（分量 2 -> 2）
洞候选 (6, 3) 不是割点（分量 2 -> 2）
... 93 个候选全部「不是割点」
```

原因很直白：`ClusterGraphAnalyzer` 缩簇时会**移除所有洞**，
所以「移除某个洞之后的图」和「完整图」在它眼里**一模一样** → 分量数永远相等 → 永远不是割点。

**修法**：判割点时用**纯邻接边**算连通分量（洞当普通格），
「移除该洞后分量数增加」= 它是割点。

**教训**

- **同一个概念在不同上下文里含义可能不同** —— 借用现成工具前先问一句「它对这个东西的处理是不是我要的」。
- **「移除前后没区别」是个强信号**：如果两个输入总是得到同样的结果，
  说明其中一个输入根本没起作用（这里就是洞被提前移除了）。
- 写这类判定时，**在注释里写清「这里洞算不算边」**，比事后靠 debug 打印快得多。

## 32. 随机游走长出来的图里没有割点

D12 要做「洞消耗后簇分裂」→ 洞必须是**割点**（删掉它，两块区域才真的断开）。

但簇是「随机游走生长」出来的 —— 游走会绕圈，簇内部**全是环**：

```
洞候选 (6, 8) 不是割点（分量 2 -> 2）
洞候选 (6, 3) 不是割点（分量 2 -> 2）
... 93 个候选，一个割点都没有
```

随机游走产生的图天然没有割点（每个点都有环上的替代路径），
所以「在块状区域里挖个洞」**永远不会让地图分裂**。

**修法：显式造出「窄口」**

```
[ 第一块子区域 ] —— [ 窄口 ] —— [ 第二块子区域 ]
```

第二块子区域的格子**不允许与第一块直接相邻**（只能通过窄口连），
于是窄口必然是割点 → 洞放在窄口上 → 消耗后这一簇真的裂成两块。

**教训**

- **要某个图论性质，就必须按那个性质去构造**，不能指望随机生成自然长出来。
  （要树就长树，要割点就留窄口）
- 随机游走 / 随机填充出来的结构，往往**恰好缺少**你需要的性质 ——
  随机不等于满足约束。

## 33. 「写了但没接线」—— 代码齐了，效果是零

D15~D19 这轮的核心发现：**五组功能全都是「骨架写了但没接线」的半成品**，
从代码上看每一处都存在、每一处都有完整实现，但**实际一个效果都没发生**。

| 组 | 看起来有 | 实际上 |
| :--- | :--- | :--- |
| 刻印 | EngravingManager.OnCardPlayed 实现了 6 种效果 | **零调用点**；且卡组每场重建 → 刻印必丢 |
| 大招 | UltimateSkill.Execute 遍历所有效果 | 只遍历 EffectIds，而**所有大招的 EffectIds 都是空的** → 效果为零 |
| 钥令 | MaxKeyOrderUsePerTurn = 2 | 管理器记一次 + 调用方记一次 → **2 次限额实际只能用 1 次** |
| 奖励选择 | RewardSystem.ApplyBattleVictoryReward | **零调用点**；只有 D4 的只读结算界面 |
| Buff/Debuff | BuffDebuffDisplay 能画图标 | 只在回合开始刷新一次；**敌人侧完全没接** |

**教训**

- **「类存在」不等于「功能存在」**。写完实现必须确认**谁调用它**、
  **调用时上下文对不对**。grep 一遍方法名，零调用点就说明没接线。
- **限额类规则要让「执行者」守门，不能指望调用方检查**。
  历史上 CanUseKeyOrder() 的检查在 BattleManager 里，
  而管理器自己照单全收 → 换个调用方就绕过限制。
  修法：管理器内部拒绝 + 返回 ool，让「超限」在**任何**调用路径下都不可能发生。
- **「每次都重建」的对象上挂的状态必然丢**。战斗卡组每场 
ew 一遍，
  刻印这类「贴在卡上」的状态必须存在**卡组之外**（autoload），
  并在卡组建好后**回填**。

## 34. 减益「挂了却毫无作用」—— 三个独立的失效原因

D19 做敌人侧状态图标时发现：减益图标画出来了，但**实际数值一点没变**。
查下来是**三个各自独立的失效原因**，任何一个单独存在都足以让减益变成纯装饰。

**原因一：靠改属性值实现，对「属性本来就是 0」的目标完全无效**

`csharp
// DefenseDownDebuff 原来的写法
target.Defense = Mathf.Max(0, target.Defense - DefenseReduction);  // 防御 0 - 10 → 还是 0
`

敌人防御本来就是 0（
ormal_wave 三个敌人：守卫 DEF=2 / 游兵 DEF=1 / 斥候 DEF=0），
**破甲对斥候等于没打**。
**修法**：减益改为**参与伤害计算**（ModifyDamageEnemy），而不是改属性值 ——
破甲 = 「受到伤害 +N%」，对任何敌人都成立。

**原因二：靠 _owner 判定归属，但没人调 SetOwner**

`csharp
// VulnerableDebuff 原来的写法
if (defender == GetOwner()) { ... }   // GetOwner() 恒为 null → 判定恒不成立
`

Enemy.AddStatusEffect **从不调用 SetOwner** → _owner 永远是 null →
**易伤从来没生效过**（大招「龙王咆哮」的毒+易伤因此打不出来）。
**修法**：改成不依赖 owner —— 易伤总是施加给承受伤害的那个敌人自己。

**原因三：减益根本没进伤害计算流程**

`csharp
// Enemy.TakeDamage 原来的写法
int actualDamage = CombatCalculator.CalculateDamage(damage, Defense);
CurrentHealth = Mathf.Max(0, CurrentHealth - actualDamage);   // 减益被跳过了
`

CalculateModifiedDamage 存在却没被调用 → 减益只影响**图标**，不影响**数值**。
**修法**：TakeDamage 里补上 CalculateModifiedDamage。

**教训**

- **状态图标正常显示 ≠ 状态生效**。要给减益写断言时，
  要断言**数值变化**（「受伤 55 而非 50」），不能只断言「图标出现了」。
- 「挂上去没反应」优先查三件事：**属性值是不是本来就是 0**、
  **判定依赖的字段有没有被赋值**、**这个状态有没有进到最终计算里**。

## 35. 同一方法被调用方和执行方各记一次账

钥令「每回合 2 次」的上限，实际只能用 1 次。

`
第 1 次使用 → ApplyKeyOrderEffect 内部记 1 次 → 调用方又记 1 次 → 计数 = 2
             → CanUseKeyOrder() 变成 false → 第 2 次直接被拒
`

**双重记账**是这类「计数器」最隐蔽的失效方式：
- 代码看起来完全正常（两处都有记录，都很合理）
- 表现是「限额比预期少一半」，很容易被当成「数值配错了」
- 但 MaxKeyOrderUsePerTurn = 2 和实际只能用 1 次之间的**倍数关系**
  才是真正的线索 —— **如果限额是 3 却只能用 1 次，就不是倍数问题**。

**修法**：计数**只在执行者（管理器）里记一次**，调用方不再重复记录；
并且让管理器**自己守门**（超限直接拒绝 + 返回 ool），
这样「超限」在任何调用路径下都不可能被绕过。

**顺带**：计数器还可能**越界**（外部误调用导致计数超上限），
GetRemainingKeyOrderUses() 这类「剩余量」接口要**钳制到 0**，不能返回负数。

## 36. 改了实现就要改文案 —— 口径漂移会让玩家学错规则

D19 把「破甲」从「降低防御值」改成「受到伤害 +N%」（因为前者对防御为 0 的敌人完全无效，见 §34）。
**代码改了，文案没跟着改** —— 玩家看到「敌人防御-10」，实际打出来是「受伤 +10%」，
于是得出一个**错误结论**：这游戏防御没用 / 数字对不上。

**本项目里受影响的文案点**（一个语义改动要同步一串地方）：

| 位置 | 内容 |
| :--- | :--- |
| KeyOrder.CreateArmorBreak().Description | 钥令自身描述 |
| KeyOrderManager.ApplyDebuffEffect 的日志 | 战斗日志里给玩家看的那句 |
| KeyOrderDescriptionUI.GetEffectDescription | 钥令说明弹窗 |
| KeyOrderSelectionUI.GetEffectDescription | 钥令三选一卡面 |
| DefenseDownDebuff.Description | 减益自身描述 |
| Data/debuffs.json 的 description | 数据表口径 |
| StatusIconFactory.GetDebuffValueText | 状态图标上的数字 |

**教训**

- **数值口径变了，名字也要跟着变**：DefenseDownDebuff.DefenseReduction
  实际含义已变成「受伤增加百分比」→ 改名为 DamageIncreasePercent，
  旧名保留为别名属性（避免外部引用编译不过）。
- **默认值也要重新想**：易伤默认值原本是 3（当时是「+3 点伤害」），
  改成百分比后 3% 几乎无感 → 改成 50。
  改口径后**一定要回头检查默认值还有没有意义**。
- **文案口径要能写进断言**：本轮加了「描述含 %」「描述不再说降低防御」
  「50 伤害实际打成 55」这类断言，把「文案与实现一致」变成**可自动检查**的，
  而不是靠人记得同步。

## 37. QueueFree 是延迟删除 —— 旧按钮会叠在新按钮上面

D7 的通用事件弹窗（EventDialog）第二次打开时，**点选项没反应、面板也关不掉**。

根因在 BuildOptions：

`csharp
foreach (Node child in _optionBox.GetChildren())
{
    child.QueueFree();      // ← 延迟删除：本帧结束前旧按钮还在容器里
}
`

QueueFree 不是立刻移除节点，而是**标记删除、等本帧结束才真正释放**。
于是第二次 ShowEvent 时：

`
第一次打开 → 容器里 2 个按钮
第二次打开 → QueueFree 标记旧 2 个（但还在）→ 又 AddChild 新 2 个
           → 容器里实际有 4 个按钮：新 2 个在下面，旧 2 个在上面
`

**玩家点到的是上面那两个旧的** —— 它们已被标记删除、但还没释放 →
点击事件不生效 → 看起来就是「点了没反应」；而新按钮被压在下面 →
面板看着"卡住"关不掉。

**修法**：先 RemoveChild 立即摘除，再 QueueFree 释放：

`csharp
foreach (Node child in _optionBox.GetChildren())
{
    _optionBox.RemoveChild(child);   // 立即从容器里摘掉
    child.QueueFree();               // 再释放
}
`

**教训**

- **QueueFree 不等于「马上消失」**。凡是「清空容器再重建」的地方，
  只写 QueueFree 就会**旧新并存**。ShopUI 早就用过 RemoveChild + QueueFree
  （见 §27「RemoveChild 替代 QueueFree」），这次同一个坑在 EventDialog 又踩了一遍。
- **症状会伪装成别的问题**：这里的现象是「按钮点了没反应」，
  很容易被怀疑成「事件回调没接上」或「状态机卡住」，
  实际上问题在**渲染层**（按钮重叠）。
  排查这类「点了没反应」时，**先打印容器里的子节点数量**——
  数量对不上就说明是重叠，不是逻辑。
- **验证要覆盖「重复打开」**：只测一次打开，永远发现不了这个问题。
  本轮的断言就是「第二次打开仍是 2 个按钮」「连开 5 次不堆积」。

## 38. 无 viewBox 的 SVG 会被 Godot 导入成 512×512 空画布

4 个图标（	eleport_entry / 	eleport_exit / skull / rrow_reserve）
的 SVG **没有 width / height / iewBox**，只有一段 path 坐标（范围约 ±31）。

Godot 导入这类 SVG 时拿不到尺寸信息 → 按**默认 512×512 画布**导入 →
path 只占画布中心一小块 → 图形被缩到很小、或者在某些容器里显示异常。

对照项目里正常的图标（intent_attack.svg）：

`xml
<svg xmlns="http://www.w3.org/2000/svg" width="128" height="128" viewBox="0 0 128 128">
`

**修法**：给每个 SVG 补上 width / height / iewBox，viewBox 按 path 的实际
坐标范围给（如 -32 -32 64 64），导入后就贴合图形实际范围了
（现在传送门图标是 61×54 / 54×60，而不是 512×512）。

**教训**

- **SVG 必须有 iewBox**，否则尺寸由 Godot 猜，行为不可控。
  写 SVG 资源时按「正常图标」的写法对齐，别从别处拷一个裸 path 就用。
- **排查图标显示异常时，先打印贴图的 get_width() / get_height()**：
  比预期大很多（比如 512）就是缺尺寸信息，比预期小就是 path 坐标画布不匹配。
- 改完 SVG 源文件后 Godot 会**自动重新导入**（.import 里的 md5 变了），
  不用手动清 .godot/imported 缓存。

## 39. 同一张图里两个元素用了两套坐标系 —— 先量清楚谁是基准

主人先报「实心六边形和青色描边不重合」，修完一轮又报「代表我的图标，和我实际所在的格子不一致」。

### 先量，别猜

这类"看着错位"必须先把**每个元素的几何中心**算出来打日志对比，
而不是凭直觉去改那个"看起来更可疑"的。

修复前（我误改之后的状态）：

`
格子节点 Position=(375,351) Size=(180,156)   ← Position 是【左上角】不是中心
HexShape 顶点中心    =(0,0)  → 画在 (375,351) = 格子左上角 ❌
HighlightLine 点中心 =(0,0)  → 画在 (375,351) = 格子左上角 ❌
玩家图标 中心在格子中心                   → 与上面两者差 (90,78) ❌
`

修复后（三方中心完全重合）：

`
格子节点 @Control@12   global rect = (870,480) 180×156   ← Position 是【左上角】
HexShape（填色）      顶点 x∈[15,165] y∈[0,156] → 中心 (90,78) → 全局 (960,558)
HighlightLine（描边）  点 (15,39)(90,0)…(15,117) → 中心 (90,78) → 全局 (960,558)
玩家图标              rect (935,533) 50×50     → 中心 (960,558)
`

### 真正的根因

`HexMapUI.HexToWorld(coord)` 返回的是格子的**左上角**（`x = 150*Q + 75*R, y = 117*R`），
`CreateTileView` 直接 `tileView.Position = worldPos` → **格子节点的原点在左上角**。
玩家图标也按「左上角 + 半个格子 − 半个图标」定位 → 同样以左上角为基准。

而规则文件 `.trae/rules/project_rules.md` 里的六边形顶点
（V0(90,0) V1(165,39) V2(165,117) V3(90,156) V4(15,117) V5(15,39)）
本来就是**相对格子左上角**写的 → **填色 `HexShape` 一直是对的**。

真正错位的是 **`HighlightLine`**：`.tscn` 里硬编码了中心原点坐标
（`(-75,-39) … (0,-78) … (75,39)`）→ 描边整体偏了 (−90,−78)，画到了格子的左上角。
这就是主人最初看到的"填色和描边不重合"。

### 我把它修反了

我当时的判断是"填色用了左上角原点 → 填色偏了"，于是把 `UpdateHexShape` 改成中心原点。
结果**把本来正确的填色改错了**：填色和描边一起跑到格子左上角，
而玩家图标还在格子中心 → 主人的第二张图「图标和所在格子不一致」。

**正确修法**：两者统一用左上角原点坐标。`HexShape` 顶点恢复规则文件那套，
`HighlightLine` 的 `points` 也改成同一套。

### 教训

- **改之前先量谁是基准**。本例里正确的是填色、错的是描边；我挑错了下手对象，
  把一个对的改成错的，还制造了一个更明显的新 bug。
- **规则文件给的坐标是相对什么原点，必须先确认当前节点的原点在哪**。
  本项目的格子节点原点在**左上角**（因为 `HexToWorld` 返回左上角），
  跟"节点通常在中心"的直觉相反。
- **同一视觉元素的多层（填充/描边/图标）必须共用同一坐标系**。
- **「看着错位但点击正常」= 纯视觉问题**，别去查点击命中逻辑
  （本项目这里命中走矩形 `Rect2`，正好绕过了多边形）。
- 排查手段一：把各元素的**几何中心**（顶点均值）打出来三方对比，偏差一目了然。
- 排查手段二：把可疑元素**涂成鲜红色**再截图 —— 形状和位置在图上一眼可辨，
  比盯着灰白色块猜靠谱得多（本次就是这样确认六边形与图标严丝合缝的）。

## 40. TextureRect 缺 expand_mode → 节点被撑到贴图原生大小

主人发现地图右上角有两个**巨大的蓝色史莱姆**（其实是 enemy_cultist.svg 的完整形象：
深蓝圆角方块 + 青色发光的笑脸），而它本该是格子中央的一个 80×80 小图标。

数据：

`
IconRect 节点尺寸 = 512×512     ← 应该是 80×80
贴图原生     = 512×512
expand_mode  = 0 (IGNORE_SIZE)  ← 问题在这
`

**根因**：TextureRect 有两个容易混的属性：

| 属性 | 作用 |
| :--- | :--- |
| expand_mode | **节点尺寸由谁决定** |
| stretch_mode | 贴图在节点内**怎么画** |

expand_mode 默认是   = IGNORE_SIZE → **节点尺寸 = 贴图原生大小**，
stretch_mode 只管贴图在这个节点里怎么缩放。
所以哪怕 .tscn 里 anchor/offset 写的是 ±40（= 80×80），节点照样被撑到 512×512。

**实测各值的效果**（custom_minimum_size = 80×80 + stretch_mode 随便）：

`
expand_mode=0 (IGNORE_SIZE)  → 节点 512×512   ← 撑开
expand_mode=1 (KEEP_SIZE)    → 节点 80×80     ← 正确
`

> 注意方向和直觉相反：**expand_mode=1（KEEP_SIZE）才是「保持我给的尺寸」**。
> 名字里的 "expand" 指的是「允许节点被撑大」，不是「保持大小」。

**修法**：给所有 TextureRect 补 expand_mode = 1（custom_minimum_size 只是下限，拦不住）。

**本项目补了 16 处**：HexTileView（格子图标）、AttackerDisplayUI（头像 + 怒气圈 ×8）、
Card（类型图标）、KeyOrderSelectionUI（钥令图标 ×3）、两个刻印选择界面（刻印图标 ×2）。

**教训**

- **TextureRect 写进 .tscn 时，expand_mode 和 stretch_mode 要成对检查**。
  只写 stretch_mode 是这个项目里最容易漏的坑（漏了就是「图标巨大化」）。
- **custom_minimum_size 挡不住撑开** —— 它只是最小值，expand_mode=0 时节点照样涨到贴图大小。
- **排查手法**：跑起来 dump 每个 TextureRect 的 size 与 	exture.get_width()/get_height()，
  「节点 > 贴图原生」就是撑开了。也可以一行扫出所有缺 expand_mode 的节点。
- 这个坑和 §38（SVG 缺 viewBox）是**同一类问题**：都是「资源尺寸信息不全 → 渲染尺寸失控」，
  但修法不同（一个补 SVG 属性，一个补节点属性）。

## 41. 位置变化有多条路径，只改一条就会漏

主人报：从传送门传送到目标点时，**迷雾没有解除**，落点周围一片黑，
看不见自己站在哪、也看不见相邻能走哪。

两条路径的代码对照：

`
走路   HexMapController.MoveTo → OnPlayerMoved      → _controller.RevealTiles(newPos, 1) + UpdateFogAndHighlight()  ✅
传送   HexMapController.TeleportPlayer → OnPlayerTeleported → 只挪图标，没照亮、没刷新迷雾              ❌
`

`TeleportPlayer` 里 `OnPlayerTeleported?.Invoke(_currentPosition)` 触发的回调，
**只做了「挪图标 + 设当前格 + 清路径高亮」**，漏了走路路径里的两行：
`_controller?.RevealTiles(newPos, 1)` 和 `UpdateFogAndHighlight()`。

**修法**：把这两行补进 `HexMapUI.OnPlayerTeleported`，与 `OnPlayerMoved` 完全一致。

**教训**

- **凡是「玩家位置变了」这件事，所有后继副作用都要逐条对齐**。
  本项目位置变化有 3 条路径：`MoveTo`（走路）、`TeleportPlayer`（传送门）、
  `TeleportPlayerTo`（调试/直接指定）。后两条里 `TeleportPlayerTo` 走的是
  `OnPlayerMoved`，所以只有传送门那条漏了。
- **「走路正常」不代表「传送正常」** —— 两条路径共用一个"效果函数"时，
  最容易只改其中一条调用点。
- **修完要跑真实链路，别只测被改的那行**。本次用临时 C# 集成测试断言 4 件事：
  落点被照亮 / 落点周围一圈被照亮 / 落点格子视图 `IsFogged == false` /
  远处格子仍是迷雾（没过度照亮），8/8 通过。
- 顺带一提：**测试断言本身也会写错**。第一次我把"照亮总数增量"写成
  `落点 + 全部邻居`，但没算上邻居里**早就照亮**的格子 → 误报 FAIL。
  `RevealTiles` 只计**新增**照亮的格子，断言必须按"新亮了多少"算。
- **autoload 里的临时测试比场景先就绪** → 拿不到 `HexMapController.Instance`
  和 `HexMapUI`。要用 `await ToSignal(GetTree(), SceneTree.SignalName.ProcessFrame)`
  轮询等场景加载完，否则测试会误判成"找不到节点"。
- **headless 跑不起来主场景**（只加载了 autoload）→ 要验 UI 必须用
  godot-runtime MCP 的 `run_project(scene="Scenes/Dev/DevScenario.tscn")`。

## 42. 「没有格子」和「有格子但走不进去」是两回事 —— 别把「洞」和「空洞」混了

主人要求：地图**中间**留些走不进去的地方（那里**根本没有格子**），
而且**逻辑要自洽：别把事件生成到不能到达的格子**。

**踩到的坑：把已有的「洞」当成了「空洞」。**

| | 洞（`HexEventType.Hole`） | 空洞（`MapQuota.Void`） |
| :--- | :--- | :--- |
| 有没有格子 | **有**，踩上去才塌陷消失 | **一开始就没有** |
| 作用 | 一次性节点，消耗后该簇裂成两块 | 地图的空白区，永久走不进去 |

如果拿「洞」去满足这个需求，会得到「格子上有个陷阱」而不是「地图中间缺了一块」——
视觉上完全不是主人要的东西。

**三条实现规则**（保证逻辑自洽）：

1. **只挖内部格子**（6 个邻居都在图里）→ 空洞是"中间的一个洞"，不是地图边缘缺了一块。
   判定要**允许"邻居已经是空洞"** —— 否则挖完第一片，旁边的格子就都不算内部了，第二片永远挖不出来。
2. **只挖不是割点的格子** → 挖完地图仍然连通，起点→终点仍然连着。
   判据用**连通块数变化**（`CountAdjacentComponents` 移除该格前后比较），
   多簇时天然是"每簇各自仍然连通"的语义。
3. **挖洞必须排在所有事件铺放之前** → 事件不可能落在被挖掉的格子上。
   再加一道**后置校验**：事件铺完后，**每个事件格都必须能从起点到达**（传送门算超边），
   不满足就重生成地图。

**顺带暴露的三个既有 bug**（都是"空洞"改动把水面下的东西顶出来的）：

- **探照灯会盖掉洞 / 盖掉传送门** —— `PlaceSearchlightTiles` 的候选只过滤了 `criticalSet`，
  没过滤 `EventType` → 洞的配额悄悄少一个、传送门配对会断。改为只落在空格上。
- **洞被撤销后不补放** —— 挖洞会改变割点集合，原本是割点的落位可能失效 →
  复检后按缺口补放。
- **沼泽落位不足** —— `PlaceSwampTiles` 遇到"不能挨着沼泽"的格子就跳过、不重试，白吃配额 →
  改为遍历全部候选（与 `PlaceRandomEvents` 保持一致）。

**另一个坑：改动生成顺序会改变整张地图。**
挖洞最初用的是生成器共用的 `_random`，每挖一格都消耗随机数 → 后续传送门 / 事件的布局全被挪动，
map_01 从「重试 0 次」变成「重试 2 次」，地图面目全非。
**修法**：挖洞用**独立的随机流**（`new Random(_seed ^ 0x5EED)`），
只在原图上"挖掉几格"，其余内容保持原样 —— 改完之后三张图都是**重试 0 次**、起终点与改动前一致。

**教训**

- **"不可到达"有两种实现**：格子存在但进不去（洞、门、单向约束）/ 格子根本不存在（空洞）。
  需求说"那个地方就没有格子"就是后者 —— 先把词对齐再动手。
- **改生成流程时，先问「会不会打乱别人的随机流」**。生成器里共用一个 `_random` 时，
  任何新增的随机消耗都会重排后面所有内容。
- **配额类"软失败"（只警告不阻断）会藏 bug**：本次是靠「挖洞 vs 不挖洞」对比
  （洞数、事件数必须一致，只少格子）才发现探照灯盖洞和沼泽落位不足的。

## 43. 同一个语义有三套实现 → 口径分叉；而且「统一」之前先分清哪个语义是对的

D20 验收时发现：`HexMap` 的公开可达性 API 在跨簇地图上把能通关的图误判成「不可达」。

**根因不是"漏了一个功能"，而是同一个语义有 3 份实现**：

`
D13 校验器    MapValidation/HexMapGraph.cs     传送门 ✅ 算
生成器内部    HexMapGenerator.BuildTeleportIndex ✅ 算（私有副本）
控制器内部    HexMapController.VerifyReachable   ✅ 算（私有副本）
HexMap 公开API  IsReachable / FindShortestPath / GetCriticalPathTiles  ❌ 不算
`

**但不能一刀切全改** —— 传送门有两种**语义相反**的处理口径：

| 用途 | 传送门 | 为什么 |
| :--- | :-- | :--- |
| 地图可达性判定（能不能通关） | **必须认** | 它是地图的一部分，是跨簇唯一的通道 |
| 自动寻路（玩家点远处格子自动走） | **必须不认** | 穿门要弹窗确认，不能自动走过去 |

`FindShortestPath` 的调用点是 `HexMapController.MoveTo`（自动寻路），
如果按"可达性"的思路把它也改成认传送门 → 玩家点一下就自动穿过传送门了，**更糟**。

**做法**：
1. **先按语义分类**，别按"看起来不一致"就统一；
2. 把两份私有副本删掉，让 `HexMap` 成为**唯一实现处**（`includeTeleports` 显式传参，**不给默认值** ——
   默认值会让人以后误用）；
3. 潜伏 bug（无调用点）也要记 —— 下一个用它做校验的人会被误导；
4. 根本解法是**删掉重复实现，只留一套**。

**这次的结果**：代码净减 85 行（3 个 `.cs` 合计 +155 / −240），实现从 3 份收敛到 1 份。
D13 校验器**保持独立** —— 它建的是带边种类的图给状态空间搜索用，
而且这一套本来就设计成"可整目录拷走复用"。

**教训**

- **"某个方法看起来不对"时，先查清有几份实现、每份的调用点是谁** ——
  改错那一份，比不改更糟（本例就是"改了寻路 = 玩家自动穿传送门"）。
- **重构统一口径时，回归基线要留档**：改完要逐项比对"重构前后同一规格生成的地图"
  （格数 / 起终点 / 空洞数），确认是**纯重构**、没顺手改了行为。
- **断言本身也会写错（第二次了）**：我一开始写"门两端只靠传送门连通"来验证"不穿传送门"，
  但 map_01 两簇在空间上连成一块、两端本来就能绕路走到 → 误报 FAIL。
  正确判据是「**路径里有没有跳传送的那一步**」（相邻两步之间不相邻 = 跳了）。
  断言失败先怀疑断言，再怀疑实现。

D21 收尾时做了一次**回读测试**（把文档里每条数字断言与代码/数据对一遍），

校验器 `Get-Anchors` 是从**整行标题**（含 `## 21. ` 的编号前缀）算的：
小写 → 去标点 → 空格转连字符。我第一次只拿标题正文去算，12 条锚点全错；
第二次手抄时又抄错一个字（「都」写成「是」），还是校验器报出来。

**教训**

- **回读检查要固化成脚本，不要靠人记** —— 已加进 `tools/check-doc-consistency.ps1`：
  ① README 规模数字（.cs 文件数 / 非空行 / .tscn / JSON 表）与实算对；
  ② 踩坑记录条数（各处声明 vs 实际标题数）；
  ③ **踩坑记录目录表必须覆盖全部条目**（编号集合比对）；
  ④ 开发计划条目数（逐项展开标题 vs 统计表 vs README 声明）。
- **校验器本身要做反向测试**：故意把 README 的条数改成 42，确认脚本报
  「写 42，实算 43」且退出码 1 —— 否则不知道它是真的在查，还是只是打印了个 OK。
- **"历史快照"与"当前声明"要分开**：变更记录里的数字不用改，
  正文里的当前声明必须改。脚本按行首 `| YYYY-MM-DD |` 排除变更记录。
- **数字口径要写清楚**：README 的行数是**非空行**，且 PowerShell 读文件
  **必须加 `-Encoding UTF8`**（否则按 ANSI 解码中文注释会截断后面的行，实测少算 520 行）。

## 45. 战斗场景「乱」的四个根因 —— 一半布局写在一半写在了代码里

主人说战斗场景「太乱了」。对比参考图（R-08 系列）后发现，乱的**不是配色也不是美术**，
是布局的组织方式：

| # | 根因 | 现象 | 修法 |
| :--- | :--- | :--- | :--- |
| **A** | **没有空间分区概念** | 全部靠 `VBox` / `HBox` 流式串联，元素随内容长度漂移 | 改成**锚定分区**：顶部条 / 玩家区 / 敌人区 / 手牌区 / 底部条，各自 anchor + offset |
| **B** | **同一信息写 3 遍** | 角色血量在「攻击体编队」「PlayerStatsUI」「PlayerZone」各一份 | 收进**一个**位置（顶部圆形头像 + 玩家区一条血条） |
| **C** | **默认灰 `Panel` 边框** | `PlayerZone` / `EnemyZone` / `HandArea` 三个 `Panel` 把画面切成三个抽屉 | 容器改成 `Control`，或给 `Panel` 覆盖**透明**样式框 |
| **D** | **坐标写在 C# 里** | `attackerDisplayUI.Position = new Vector2(200, 10)` 这类硬编码散在 `BattleManager` 里 | 位置全搬进 `.tscn` 的锚定容器，代码不再写坐标 |

**最隐蔽的一条**：`.tscn` 里 `anchors_preset = 10`（顶宽）时，`offset_right` **不是绝对位置**，
而是「相对右边锚点的偏移」。我给 `TeamSlot` 写了 `offset_left=16, offset_right=436`，
结果它的真实宽度是 `1920 + 436 - 16 = 2340` → 里面的编队被 HBox 居中推到了屏幕中间偏右。
**固定宽度的容器要用 `anchors_preset = 0`（左上角）**，`preset 10` 只能配 `anchor_right = 1.0` 一起用。

**配套的三个小坑**：

- **给 `TextureRect` 加 `panel` 样式框不生效** —— 原来「怒气圈」是一个 `TextureRect`，
  代码给它 `AddThemeStyleboxOverride("panel", ...)`，怒气**其实一次都没画出来**。
  换成自绘的 `RageCircle`（`Control` + `_Draw`）才真的画出弧。
  → **`TextureRect` 想要圆角/描边，要用 `Panel` 包一层或换自绘控件。**
- **`HBoxContainer` 里不设 `size_flags_horizontal = 3` 的 Label 会被挤成 1 像素** ——
  卡牌名称（`clip_text = true`）直接消失。**带 `clip_text` 的 Label 必须给 expand。**
- **`Node not found` 的报错来自 `GetNode` 不是 `GetNodeOrNull`** —— 删掉场景节点后
  脚本还在 `GetNode` → 每次进战斗都刷一屏栈回溯。

**教训**

- **「乱」优先怀疑布局组织方式**，不要先改美术：分区 → 去重 → 去框 → 搬坐标，四步做完观感立刻不一样。
- **凡是能写进 `.tscn` 的，不要写在 C# 里** —— 坐标写死在代码里，改一次布局就得改一次代码，
  而且没法在编辑器里调。

## 46. 「存在一条走法」≠「怎么走都行」—— 洞放在旁支窄口会制造死局

主人把要求说清楚了：**「从起点出发，战斗都赢的情况下，无论怎么走都能到终点见到 BOSS」**。
这比原来的要求强一档 —— 原来的 D13 校验器给的是**存在性**保证（「存在一条走法能通关」），
主人要的是**全称**保证（「任何走法都不会把玩家困死」）。

**改之前的实测（三张图全部不合格）**：

```
map_01  CanCompleteGoal=True   但死局状态 10 个
map_02  CanCompleteGoal=True   但死局状态 12 个
map_03  CanCompleteGoal=True   但死局状态 12 个
```

**死局是怎么来的**：洞是**消耗型**格子 —— 踩上去还能站，离开时**该格被删除**。
旧规则把洞放在「簇的窄口」（旁支的入口）上：

```
玩家走进旁支 → 踩洞 → 洞被消耗 → 旁支入口消失 → 玩家被困在旁支里 → 永远到不了 BOSS
```

静态层查不出这个（洞还在时，旁支仍能经由洞回到终点 → 不算软锁），
只有**状态空间**（把「哪些洞已被消耗」也当状态）才看得见。
而旧的状态空间搜索是**一找到通关走法就 return** —— 只验存在性，验不出"别的走法会死"。

**修法（两处）**：

1. **校验器加全称判定**（`MapValidator.SearchDeadEndStates`）：
   ① 正向枚举所有可达状态（位置 / 已消耗洞集合 / 进洞来源格）并记录状态间的边；
   ② 建**反向边**，从「站在终点」的状态反向 BFS → 得到「还能到终点的状态」集合；
   ③ 可达状态里不在那个集合里的，就是**死局状态**。
   状态转移规则抽成 `TryStep()` 一份实现，存在性搜索与全称搜索共用（别抄第二份）。
2. **生成器的洞落位改成「试放 + 裁决」**：逐个候选格试放一个洞，跑一次全称判定，
   通过就留下、不通过就撤掉换下一个。**判据只有校验器那一份实现**，生成器不自己再抄一遍。

**顺带修掉的冗余**：旧的「洞必须是割点 → 不是就撤销 → 再补放」那套被整段删掉了 ——
新落位已经自带全称判定裁决，而且旧判据（纯邻接算割点）在跨簇地图上本来就是错的。

**改之后的实测**：

| 地图 | 全称判定 | 死局状态 | 洞数/配额 | 重试 | 问题数 |
| :--- | :-- | :-- | :-- | :-- | :-- |
| map_01 | True | **0** | 2 / 2 | 0 次 | 0 |
| map_02 | True | **0** | 3 / 3 | **1 次** | 0 |
| map_03 | True | **0** | 3 / 3 | 0 次 | 0 |

> map_02 那 **1 次重试**是新门控真的在拦人：第一次生成的图有死局 → 被拦下 → 换了一张。
> 这就是「门控有效」的证据，不是 bug。

**教训**

- **「有没有解」和「所有解都安全」是两个问题**。只验前者会漏掉
  "玩家随便走都能把自己走死"这类问题 —— 而且它恰恰是最容易被玩家踩到的。
- **存在性判定是"乐观"的**：它默认玩家会走对路。全称判定才是"玩家乱走也死不了"。
- **消耗型节点（洞/可破坏地形）是地图设计里最危险的东西**：
  它的「不可逆」会让一个原本安全的旁支变成死胡同。设计它时必须问：
  **"消耗掉它之后，我这一侧还能到终点吗？"**
- **判据要唯一**：生成器自己再抄一份"什么算安全洞"的规则，迟早和校验器分叉
  （见 §43）。让生成器**直接调用校验器**来裁决，是最省事的做法。

## 47. 元素「看不见」往往不是没画，是被后画的兄弟节点盖住了

**现象**：战斗场景左上角 4 个角色头像「不见了」，而且**整个顶栏**（血量、回合、角色名）都发灰偏暗。

第一反应是「头像资源没加载」—— 但运行时查 `AvatarRect.texture` 得到的是
`res://Assets/Portraits/avatar_rat.svg`，采样纹理像素是 `#A39AB6` / `#D8C8E8`（**亮色**），
说明**资源没问题**，问题在渲染。

**根因**：`CommonHUD` 顶层有个铺满顶部 120px 的 `ColorRect`：

```
color = Color(0.08, 0.09, 0.12, 0.92)
```

它在 `UI` 里的**位置排在 `TopBar` 之后** → Godot 按子节点顺序绘制 → **后画的盖在先画的上面** →
92% 不透明的深色板把整个顶栏压暗了 8 成。头像一直在画，只是**被盖住了**。

**教训**

- **「看不见」要先分清三种情况**，排查手段完全不同：
  - **没画** → 查节点存不存在、脚本有没有跑、事件有没有触发
  - **没加载** → 查 `texture` 路径，并**直接采样纹理像素**（像素是亮的就说明导入没问题）
  - **被盖住** → 查**绘制顺序**：同一个父节点下，排在后面的兄弟节点会盖住前面的
- **染色实测最快**：把可疑节点 `self_modulate` 设成红色再截图。
  被盖住的东西纹丝不动、盖在上面的东西立刻变红 —— 一次定位，不用猜。
  （这次就是靠这个排除了「资源没加载」和「modulate 被改」两种可能。）
- **半透明底板是「场景级」的东西，不该由「组件级」的 HUD 默认带着**。
  `CommonHUD` 原本是给地图场景用的顶栏（那里它就是全屏顶栏，底板合理）；
  战斗场景后来自己做了 `TopBar`，但 `CommonHUD` 还留在 `UI` 里当兄弟节点 → 冲突。
  解法不是删掉别人的底板，而是加 `ShowBackground` 导出开关
  （沿用 `ShowTeamSection` / `ShowStatsSection` 的既有模式），**谁不需要谁关**。
- **同一个 `CanvasLayer` 下的兄弟节点顺序 = 叠放顺序**。
  重排布局时（尤其是把某个组件从场景里挪进另一个组件时）要顺手确认它排在谁前面。

## 48. 方法体被压成一行时，行尾注释会把后面的代码一起吃掉

**现象**：主人要求「给怪物和玩家血条下方加几个测试的 buff 图标看看」，
结果**敌人侧图标出来了，玩家侧一个都没有**。

**根因**：`BattleManager.UpdateBuffDebuffDisplay()` 的**整个方法体被压成了一行**：

```csharp
// 玩家侧状态条在 PlayerZone 里（血条下方那排图标）		if (playerZoneUI == null) return;		playerZoneUI.SetStatus(player?.StatusEffects);
```

`//` 是**行尾注释**，会把**这一行剩下的全部内容**都吃掉 ——
包括 `if (playerZoneUI == null) return;` 和 `playerZoneUI.SetStatus(...)`。
方法体变成空的 → 玩家侧状态条**从来没被刷新过**。
敌人侧是另一个方法（`UpdateEnemyStatusIcons`），所以一直正常 ——
**一个坏一个好，掩盖了问题**。

**教训**

- **编译能过 ≠ 代码在跑**。这段代码语法完全合法，编译器一声不吭，
  但它已经变成了注释。**「方法体被压成一行」是编辑事故的高发形态**：
  写文件时把换行丢了，之后所有针对该文件的编辑都可能静默失真。
- **别用「编译通过」代替「确实执行了」**。这次是靠日志里
  `[BuffDebuffDisplay] RefreshStatus called` 一直没出现才定位到方法没被调用。
- **一条语句一行不只是风格，是安全约束**：C# 里 `//` 后面的内容整行失效，
  多个语句挤一行时，只要前面有注释，后面全部作废。
- **同一语义的多个实现要一起查**：玩家侧和敌人侧各有一个刷新方法，
  不能凭「另一个是好的」推断「这个也是好的」。

## 49. git 比对远端前先关掉 quotepath，否则中文路径全变假差异

**现象**：做「回读测试」（把远端内容拉回来跟本地逐字节比对）时，
拿 `git ls-files -s` 的路径去跟 GitHub API 返回的路径对，
结果报出 **「仅本地有 55 个」「仅远端有 55 个」** —— 明明是同一个文件。

**根因**：git 默认 `core.quotepath=true`，会把**非 ASCII 路径输出成八进制转义并加引号**：

```
"docs/screenshots/\346\230\237\346\210\230\347\205\253\347\233\233.jpg"
```

而 GitHub API 返回的是**真实 UTF-8 路径**：

```
docs/screenshots/探照灯生效后.jpg
```

两边字符串永远对不上 → 一大批假差异。本项目的中文文件名特别多
（`docs/screenshots/战斗2.jpg` / `docs/开发计划.md` / `docs/踩坑记录.md`…），所以必踩。

**做法**

- 比对前一律加 `-c core.quotepath=false`：
  `git -c core.quotepath=false ls-files -s`
- **先看「内容不一致」这一项**再下结论：同名文件的 blob SHA 是否相同。
  本次「内容不一致 = 0」已经说明文件其实全对，55 个差异纯粹是路径编码问题。
- 真正的「不一致」长这样：**只有刚改完还没提交的那几个文件**会不同
  （本地工作区是新内容、远端是上次提交的内容）—— 这是预期，不是推送失败。

**配套：回读测试的完整打法（本次实测）**

1. `GET /repos/{owner}/{repo}/git/trees/main?recursive=1` 拿远端**文件树**（含每个文件的 blob SHA）
2. 本地 `git -c core.quotepath=false ls-files -s` 拿本地 blob SHA
3. 两边按路径对齐 → 比 SHA：本次 **883 个文件全部一致**
4. 再对改动过的文件做**字节级**校验：GitHub **contents API** 返回 base64，
   本地解码后算 SHA256 对比（本次 31 个文件里 28 个逐字节一致，
   另外 3 个正是「刚改完还没提交」的那几个）
5. `raw.githubusercontent.com` 那条路**本机拉不动**（连接被重置），
   改用 contents API 才通 —— **换一条抓取路径，别在一条超时的路上死等**

> ⚠️ 坑点提醒：`git ls-files -s` 输出的路径**带引号**（含空格/特殊字符时），
> 拆分时要用 `-split '\s+', 4` 并把第 4 段开头的 `"` 去掉。

## 50. 扇形排布的卡牌，命中检测必须按牌的真实变换来判

**现象**：手牌是扇形排开的（每张牌都转着角度）。
鼠标移过去时，**最两边的牌经常"查看到了错误的牌"** —— 明明指着右边那张，亮起来的是左边那张。

**根因**：命中检测用的是**未旋转的轴对齐矩形**：

```csharp
// ❌ 之前的写法：矩形是按「没转过来」的卡牌位置算的
Rect2 cardRect = new Rect2(containerGlobalPos.X + x, containerGlobalPos.Y + y, _cardWidth, _cardHeight);
if (cardRect.HasPoint(mousePos)) { newHoveredIndex = i; break; }
```

而画面上的牌是**转着的**。弧度越大、偏离中心越远，
「视觉上属于这张牌」的区域和「未旋转矩形」差得越多 ——
**两端的牌差得最厉害**（中间几张几乎重合，所以看不出问题）。

而且遍历是从左到右 `break` 的 → 命中的是**最左边**那张，
不是视觉上压在最上面的那张 → 系统性地偏左。

**改法**

1. **按牌的真实变换判定**：把全局坐标反变换到牌面局部坐标，再判局部矩形：

```csharp
public bool ContainsGlobalPoint(Vector2 globalPos)
{
    Vector2 local = GetGlobalTransform().AffineInverse() * globalPos;   // 含旋转与缩放
    return new Rect2(Vector2.Zero, Size).HasPoint(local);
}
```

2. **遍历顺序反过来**：从最上面那张往下找（后加入的牌 Z 更高、压在上面），
   命中的要和眼睛看到的那张一致。

3. **顺手把弧度降下来**（±18° → ±7°）：弧度小了，命中误差本来就小，
   两端的牌也不再歪得那么厉害。

**教训**

- **命中检测必须用「渲染时用的那个变换」**，不能用「布局时算出来的那个矩形」。
  只要控件带了 `rotation` / `scale`，两者就不等价了。
- **重叠的兄弟控件，命中要按绘制顺序（z 序）从高到低找**，
  否则永远命中「先加进来的那个」，而玩家看到的是「后加的那个压在上面」。
- **UI 摆歪了最容易先在两端出问题** —— 中间部分的重叠区掩盖了误差。
  测的时候要专门测**最左和最右**那一张。

## 51. 迷雾画成近黑色六边形，不等于遮住了地形

**现象**：主人说「迷雾不应该只盖住没发现的格子，也要盖住不能走但还没打开的地方，即使是没有格子。
否则这个迷雾就只能遮蔽事件，遮蔽不了地形。」

**根因**：未照亮的格子被画成了**近黑色的六边形**（`Color(0.02, 0.02, 0.04)`），
而「没有格子的空洞区」是**背景色**（深蓝灰）。

两片区域**颜色不同** → 玩家一眼就能看出：黑色蜂窝 = 路径，空隙 = 空地。
也就是说，迷雾只遮住了格子里的**事件图标**，**地形（整条路径的形状）原封不动地露着**。

实测数据（map_01，56 格）：照亮 6 格，其余 **50 格全是近黑色六边形**，
和背景色的空洞区形成了明显的形状对比。

**改法**：未照亮的格子**整个不画**（`Polygon2D` 透明）。
这样未探索区 = 一整片背景色，跟「没有格子的空洞区」完全一致 →
**地形和事件一起被遮住**（对照参考图 R-05 的「纯黑虚空区」）。

**顺带发现并修掉的两个洞**

1. **迷雾里的格子照样能收到鼠标事件**（控件还在，只是画成透明）。
   `OnTileHovered` 原来不判断是否已照亮 → 鼠标扫过迷雾区会**把整条路径点亮**，
   地形又泄出去了。已加 `IsRevealed(coord)` 判断。
2. **一次性事件的图标不会被清掉**：`HexTile.Trigger()` 只把 `EventType` 清成 `Empty`
   （所以事件不会二次触发），**但 `IconPath` / `DisplayName` 都原样留着**
   → 探照灯"打开开关"之后，灯笼图标仍然挂在格子上，看起来还能再按一次。
   已在生效时**遍历全图**把 `DisplayName == "探照灯"` 的格子清空。

**教训**

- **"遮住内容"和"遮住形状"是两件事**。把元素画成深色只是遮住了内容，
  它的**轮廓**照样在泄信息。真正的遮蔽 = **不画**（或画成与周围完全一致）。
- **判断"有没有藏住"要看它和背景的对比度**，不能只看"内容是不是空的"。
  本例中事件图标确实没了，但六边形轮廓和背景的明暗差把地形全交代了。
- **一次性事件的"用完"要清全套状态**：`EventType` 清了不算完，
  `IconPath` / `DisplayName` / 层数这些**表现层字段也要一起清**。

## 52. 补间进度不能在事件回调里推进

**现象**：主人说「我鼠标**持续按**在一张卡牌上的时候，放大效果是**非常缓慢**的」。

**根因**：卡牌拖拽的放大进度（`_dragBlend`）是在**鼠标移动事件的回调里**推进的：

```csharp
// ❌ 之前的写法
public override void _GuiInput(InputEvent @event)
{
    if (@event is InputEventMouseMotion && _dragPhase != DragPhase.None)
    {
        UpdateDrag(...);      // ← 进度只在这里推进
    }
}
```

**鼠标按住不动时就不会再产生移动事件** → 进度永远停在半路 → 卡牌一直是"半大不大"的样子。
看起来像"动画很慢"，**其实是卡住了**（而且拖得越久越明显，因为一次移动事件就推一大截）。

**改法**：把进度推进放到**每帧都跑**的地方（`_Process`），事件回调只负责更新"鼠标在哪"：

```csharp
public override void _Process(double delta)
{
    if (_dragPhase != DragPhase.None)
    {
        _dragBlend = Mathf.MoveToward(_dragBlend, 1f, (float)delta * DragBlendSpeed);
        ApplyTransform();
        return;
    }
    ...
}
```

实测：按住不动，**0.15 秒**就放大到位（`t=0.05s → 1.47`，`t=0.15s → 1.5`）。

**教训**

- **补间的进度要由"时间"驱动，不是由"事件"驱动**。
  凡是「按住 / 拖拽 / 持续按住」这类交互，动画进度一律放 `_Process`，
  事件只提供"当前状态"（位置、是否按下）。
- **"很慢"和"卡住"要分清**：先量一下数值随时间的变化
  （这次是 0.05s / 0.15s / 0.35s 三个采样点），一看就知道是"慢"还是"到不了顶"。
- 顺带一提：同类的还有**扇形手牌的横向间距**——
  以前「固定半径 + 固定角度」把间距和角度**耦合**了（间距 = 2R·sin(A)/(n-1)），
  牌越多挤得越近（8 张时只有 35px）。
  正确做法是**先定间距、再由间距反推半径**，牌数变了间距也不变。


## 53. 数据表写了不等于代码读了：先量运行时对象的字段，再动手修

**现象**：主人报「打出 `rabbit_special` 后，敌人血条下方**没有状态图标**」。
上一轮已查清并记录了原因：`Card.CreateBuffFromCard()` 用 `switch` 直接 `new` 裸 buff、
绕过 `EffectRegistry` → 裸 buff 没有 `IconPath` → 图标画不出来。
**修法都写好了（约 5 行），照着改完，图标依然不出来。**

**根因（真正的那个，在更上游）**：修的那一层**根本不是断的地方**。
运行时实测（用 `run_script` 把手牌里的卡对象字段 dump 出来）：

```
手牌 rabbit_special | 兔特殊技 | ApplyBuffName=[]  ApplyBuffDuration=0  BuffValueBase=0
```

卡牌对象上**增益字段是空的** —— 而 `Data/character_cards.json` 里这张卡明明写着
`"applyBuffName": "strength"`。
顺着往上查：`BattleManager.InitializeCards()` 用的是 `attacker.GetTeamDeck()`，
而 `Attacker.CreateCardFromId()` 是**纯代码硬编码**的：
名字拼「角色名 + 特殊技」、费用按 id 后缀猜、特殊技**不打伤害不给护盾**。
**`character_cards.json` 那 96 张卡的数据从来没进过战斗**（它只被刻印列表和美术脚本读）。

**数据表里唯一带 `applyBuffName` 的卡是 `rabbit_special`，
而它压根没带这个字段进战斗 → 增益从来就没被创建过 → 图标当然没有。**
前面那条「裸 buff 没有 IconPath」的结论**本身没错，但被更上游的断点挡住了**。

**教训**

- **「修 A 会让 B 变好」不是证据，是假设。** 上游断了的时候，下游怎么修都不会好。
  动手前先确认**那个字段在运行时对象上到底有没有值**。
- **量运行时对象，别只读代码。** 代码读起来「明明解析了 applyBuffName」，
  但那行解析属于**另一条根本没走的代码路径**。
  验证手段：用 `run_script` 从场景里捞出真实对象 dump 字段（`hand` 里的 `CardUI.GetCardData()`）。
- **症状要往上游追到「数据第一次变成运行时状态」的那一层**：
  `JSON → 加载器 → 运行时对象 → 表现层`。本例断在第一段和第二段之间。
- **数据表和代码两套真相并存时，先确认哪套真的在跑** ——
  `CharacterCardLoader` 有 3 个调用点，全是「刻印可选卡牌列表」，**没有一个是战斗卡组**。
- 附带发现：`Data/character_cards.json` 里有**两张卡重名**
  （`狡兔三窟` = rat_defense + rabbit_defense，`猛虎下山` = tiger_attack + tiger_special2）。
  名字以前不显示所以没人发现；数据一进战斗，玩家就能在同一个卡组里看到两张同名牌了。


## 54. 卡面文案与实际效果必须同源：数值、对象、时长三样都要对得上

**现象**：卡面写着「获得 攻击力 +50，持续 1 回合」，实际打出去只有 +3，而且落在**敌人**身上。

**根因**：同一个概念在三个地方各有一份口径：

| 口径 | 卡面文案 | 实际效果 | 后果 |
| :--- | :--- | :--- | :--- |
| 数值 | 卡牌数据的 `buffValueBase` | 配置表 `buffs.json` 的值（力量=3） | 卡面 +50、实际 +3 |
| 作用对象 | 「获得…」（=自己） | `GetTargetFromCard()` **永远取敌人** | 增益卡其实是「给敌人加攻」 |
| 时长 | 卡牌数据的 `applyBuffDuration` | 同上（缺字段就是 0 → 挂上就过期） | 状态一闪而过 |
| 怒气 | 卡牌等级系统的 `5 + perLevel` | `RageManager` 硬编码的 15 / 10 | 卡面写 5、实际给 15 |

**改法**：**每个数字只能有一个出处**。

- 数值：卡牌数据是唯一真相源 → 效果对象的数值字段由卡牌数据写入（`ApplyBuffValue`）。
- 时长：卡牌指定优先，缺省回落配置表（0 不再出现）。
- 怒气：抽一个 `RageManager.GetRageForCard(card)`，**卡面文案和战斗结算都调它**。
- 作用对象：卡面措辞跟着**实际**改（增益也落在敌人身上 → 写「目标获得…」而不是「获得…」）。

**教训**

- **「文案与实现一致」不是文案的事**：只要文案和实现读的是不同来源，
  迟早会漂。每次改语义（像 D19 的破甲改成百分比）要**同步文案 + 数据 + 实现**三处。
- **同一口径散在多处时，先抽成一个函数**，再让两边都调它；
  否则改了一处忘了另一处，下一轮又会漂回去。
- **数值改动前先量它落在谁身上**：本例 50 如果真按 50 生效，落在敌人身上
  就是「敌人攻击 6 → 56」，玩家 125 血两回合就没了 —— 数值错 + 对象错 = 双重放大。
- 效果类里不同的效果数值字段名字不一样（`AttackBonus` / `DefenseBonus` / `HealPerTurn`…），
  只能按类型分派；**没有对应字段的要打警告**，不能静默丢掉数值。


## 55. 生成脚本默认「不覆盖」：手改过的产物不能被一次重跑冲掉

**现象**：`tools/generate-card-art.ps1` 生成的 121 个 SVG 里，
有 73 个已经被主人**手工精修**过。但这个脚本是「新增卡只要改 JSON 再跑一次」用的
—— 也就是说，**最容易发生的操作恰好是会毁掉手改成果的操作**。
之前脚本头部只加了一句警告文字，警告挡不住手滑。

**改法**：**默认不覆盖**，要重生成必须显式 `-Force`：

```powershell
function Write-SvgFile {
    param([string]$Path, [string]$Content)
    # 默认不覆盖已存在的文件（保护手工精修过的美术）；要重生成就加 -Force
    if ((Test-Path -LiteralPath $Path) -and (-not $Force)) { return $false }
    ...
}
```

配套两点：

- **报告要如实**：`已生成 N 个 / 已保留 M 个`，不要只报「已生成 121 个」（那是在骗人）。
- **自检分级**：这次**真正写出来**的文件不过自检 → 失败退出码 1；
  「保留没动」的文件（可能是手工精修的）只报警告 ——
  不该让脚本因为别人的成果退出码非零。

**验证**（在临时副本上做，不碰真仓库）：全新目录 → 生成 121 个；
手改其中一个 → 默认再跑 → SHA256 不变（手改还在）；
加 `-Force` → SHA256 变了（手改被冲掉）。
真仓库上跑默认模式 → 140 个 SVG **内容零变化**（`git status` 干净）。

**教训**

- **「生成器脚本」默认必须是幂等且保守的**：覆盖要显式要，覆盖前要报数。
- **警告文字挡不住误操作**，要用**机制**挡（默认不覆盖 + 显式开关）。
- 脚本自检也要**分级**：自己的产出不过就失败，别人的产物有问题就提醒。
- 验证破坏性行为时，**在临时副本上做**（脚本支持 `-RepoRoot` 参数就是为此），
  别在真仓库上试「看看会不会坏」。


## 56. C# 导出属性在 .tscn 里要用 **PascalCase**，写错不报错、只是不生效

**现象**：给 `BuffDebuffDisplay` 加了一个导出属性，想让玩家侧的状态图标靠右排：

```csharp
[Export]
public int IconAlignment { get; set; } = 1;
```

在 `PlayerZone.tscn` 的实例上按 GDScript 的习惯写成 `icon_alignment = 2`。
**运行时纹丝不动**：图标容器仍是居中，`IconAlignment` 读出来还是 1，
**控制台连一条错误都没有**（Godot 对 .tscn 里不存在的属性是静默忽略）。

**根因**：**GDScript 的导出属性用 snake_case，但 C# 的导出属性在 Godot 里保留 PascalCase 原名**。
运行时用 `node.get_property_list()` 一看便知：属性名就叫 `IconAlignment`，
不是 `icon_alignment`。本项目里已有的例子都是 PascalCase：
`ShowBackground = false` / `ShowTeamSection = false` / `SlotScene = ExtResource("3")`。

**改法**

```
[node name="BuffDebuffDisplay" parent="." instance=ExtResource("2")]
layout_mode = 2
IconAlignment = 2
```

改完实测：`IconAlignment = 2` → 图标容器 `alignment = 2`（靠右）✓。

**教训**

- **.tscn 里 C# 导出属性一律 PascalCase**（照抄同项目里已有的写法，别照 GDScript 的习惯猜）。
- **「属性不生效」且「没有报错」= 大概率是属性名拼错**：用 `get_property_list()` 看真实名字，
  别猜。
- 验证手段要选**能读到属性值**的那种：光看画面没变化，说明不了是导出没传进去还是代码没执行；
  直接 `node.get("IconAlignment")` 读一眼就知道。


## 57. `.tscn` 里子节点的 `parent` 路径是相对**场景根**的，不含根节点名字

**现象**：新建 `Scenes/UI/DeckStatusPanel.tscn`，子节点写的是：

```
[node name="HandGroup" type="HBoxContainer" parent="."]
[node name="HandCount" type="Label" parent="DeckStatusPanel/HandGroup"]   ← 错
```

结果：**所有子节点都没被创建**，控制台刷：

```
WARNING: Parent path './DeckStatusPanel/HandGroup' for node 'HandCount' has vanished when instantiating
[DeckStatusPanel] 未找到 DrawButton 节点，抽牌池图标无法点击
```

**根因**：`parent=` 的路径是**相对场景根**的，**不含根节点自己的名字**。
根节点下面的直接子节点写 `parent="."`，孙节点写 `parent="HandGroup"`（或 `"HealthRow/HealthStack"` 这种多级路径）。
我按「节点全路径」的习惯写了 `DeckStatusPanel/HandGroup` → Godot 去找 `./DeckStatusPanel/HandGroup`，
而场景根下的 `DeckStatusPanel` 指的是**根自己**，找不到 → 父节点「消失」→ 子节点被丢弃。

> 对照：本项目已有的 `PlayerZone.tscn` 里是 `parent="HealthRow/HealthStack"` ——
> **没有** `PlayerZone/` 前缀，就是这个规矩。

**教训**

- **手写 .tscn 时，`parent` 一律从根的下一层开始写**，别带根节点名字。
- 症状是「**节点凭空消失**」而不是「报错」→ 看到 `Parent path ... has vanished` 就往这里查。
- 这类坑光看代码看不出来：**写完必须跑一次**，`GetNodeOrNull` 拿到 null 的打错误日志是本项目的兜底
  （本例正是 `[DeckStatusPanel] 未找到 DrawButton 节点` 这条日志把人指到了正确方向）。

**现象**：新增 3 个图标 SVG（`Assets/Icons/hand_cards.svg` 等），在 `.tscn` 里引用后跑游戏：

- 「文件明明在磁盘上却说不存在」→ 先怀疑**没导入**，不是路径写错。


## 59. 百分比化之后绝对值字段恒为 0 —— 直接读 `card.Damage` 的地方全部静默失效

**现象**（2026-10-24）：卡牌数值改成「角色属性 × 百分比」之后，**防御卡在战斗里不再显示蓝色样式**，
刻印选卡列表里**所有卡都没有伤害 / 护盾数字**，卡牌升级预览**整段空白**。

**根因**：数值改成百分比后，`Card.Damage` / `Card.ShieldGain` 这两个绝对值字段**一直是 0**
（数据表里已经没有 `damage` / `shieldGain` 了）。而全项目有 6 处仍在直接读它们：

| 位置 | 读法 | 后果 |
| :--: | :--- | :--- |
| `CardUI.UpdateCardStyle` / `UpdateGlowIntensity` | `cardData.ShieldGain > 0` | 防御卡掉进「普通卡」配色（灰/紫），没有盾牌图标 |
| `CardSelectionItem.GetCardEffectText` | `card.Damage` / `card.ShieldGain` | 刻印选卡列表数值全空 |
| `DescriptionGenerator.GenerateUpgradePreview` | `card.Damage > 0` / `card.ShieldGain > 0` | 升级预览什么都不显示 |
| `EngravingManager.ApplyCopyEffect` | 手抄字段（没抄百分比） | 复制出来的卡算不出伤害 = 0 |
| `CardEffectResolver`（遗留结算路径） | `card.ShieldGain` | 哪天接回去就是「0 伤害」 |
| `BattleManager` 的卡组日志 | 打印 `card.Damage` | 日志误导成「所有卡都没伤害」 |

**改法**：**一切数值读取都走 `card.GetFinalDamage(attributes)` / `card.GetFinalShield(attributes)`**，
判定「是不是防御卡」走 `card.IsDefenseCard()`（三个信号任一成立即是：卡位标记 / 绝对值护盾 / 护盾百分比）。

**教训**

- **改数值模型时，要用 grep 把「所有读旧字段的地方」一次找齐** ——
  改完数据表才发现界面少了一半表现，是因为「字段还在、只是恒为 0」，**编译不报错、运行不报错、只是静默变空**。
- **日志要打印最终值**（`GetFinalDamage`），不是打印原始字段 ——
  一行 `Damage: 0` 能让人以为「卡牌没伤害」，实际是「日志读错了字段」。
- 加一条 `IsDefenseCard()` 这类**统一判定**，别让「防御卡」在 4 个地方各判一次。


## 60. 界面侧不要直接用共享的卡牌模板实例

**现象**：刻印选卡列表 / 战斗奖励选卡里，卡牌的伤害与护盾**显示为 0**；
而且两个界面拿到的居然是**同一个 `Card` 对象**（谁改了等级 / 费用都会互相影响）。

**根因**：`CharacterCardLoader.GetCharacterCard(id)` 返回的是**数据表里的共享模板实例**。
战斗里因为要改费用 / 等级 / 刻印，所以走的是 `template.Clone()`；
但**界面侧直接用了模板本身** —— 模板既没挂角色属性（百分比算不出数），又是全局唯一的一份。

**改法**：新增工厂，界面侧一律走它：

```csharp
// CharacterCardLoader
public static Card CreateInstance(string cardId, CharacterAttributes attributes = null)
{
    if (!TryGetCharacterCard(cardId, out Card template)) { /* 报错 */ return null; }
    Card instance = template.Clone();
    if (attributes != null) instance.LinkedAttributes = attributes;   // ← 百分比要靠它
    return instance;
}
```

调用方（`HexMapUI` / `BattleRewardUI`）传 `character.GetAttributes()`。

**教训**

- **「查数据的函数」和「拿来做实例的函数」要分开**：前者给模板，后者给副本。
  返回模板的 API 名字里最好带 `Template` 字样，让人一眼看出不能直接用。
- **百分比数值必须有「角色属性」才能算出来** → 谁造实例谁负责挂属性，
  漏挂就静默显示 0（和 §59 是同一个病的两个入口）。
- 顺手：`EngravingManager` 复制卡牌时**别手抄字段**，直接 `originalCard.Clone()` ——
  手抄一定会漏新字段（这次就漏了 `DamagePercent` / `ShieldPercent`）。


## 61. 数据表缺字段是**静默**的：12 生肖的 `attackCardId` 一直是空串

**现象**：`Data/characters.json` 里 12 个生肖角色**只有 `defenseCardId`**，没有 `attackCardId`；
只有后加的波吕克斯两个都有。加载器读成空串后**没有任何报错**。

**为什么没炸**：角色属性（`CharacterDefinition`）当时是在**代码里写死**的（`CreateRat()` 里
`AttackCardId = "rat_attack"`），选人界面用的也是代码那份 → 数据表缺字段根本没被走到。

**为什么还是得修**：数据表是「唯一真相源」的方向（D29 立的规矩），
一旦哪天改成以 JSON 为准，这 12 个角色就会**没有打击卡**（队伍少 4 张牌，且不报错）。

**改法**：数据补齐（12 行 `attackCardId`）+ 加可重复执行的校验：

```powershell
powershell -ExecutionPolicy Bypass -File tools\check-card-data.ps1
```

它检查：每个角色的两张基本卡非空 / **基本卡 id 全局唯一**（不许两个角色共用）/
引用的卡存在且归属正确 / 基本卡按百分比配数值 / 没有孤儿卡。

**教训**

- **加载器给字段的默认值会掩盖「数据没配」** —— `ContainsKey(...) ? ... : ""` 这种写法
  在缺字段时既不报错也不留痕，只在**切到那份数据**时才炸。
- 「代码里有一份 + 数据表里有一份」= 两份真相源。**两份都得补齐**，
  并且要有脚本守着，否则不知道哪份是真的。
- **校验脚本要校验「唯一性」这类结构约束**，不只是「引用存在」——
  「两个角色共用一张卡」这种事，`grep` 查不出来，但脚本一秒能查出来。


## 62. 后台模式下模拟鼠标移动不生效，拖拽类交互要用脚本直接调方法

**现象**（2026-10-24）：给卡牌加「长按放大」时，用 MCP 的 `simulate_input` 测拖拽出牌 ——
按下和松手都命中了正确的卡牌，**但鼠标移动事件报告的坐标从头到尾没变**，
于是卡牌永远到不了「上移 110px = 松手即出牌」的阈值，只会被当成「取消」。

**根因**：`run_project(background=true)` 会**屏蔽物理输入**（窗口在屏幕外、抢不了鼠标），
`simulate_input` 的 `mouse_motion` 在这个模式下不产生真实位移；
但 `mouse_button` 的**按下 / 松手**是程序注入的，照常生效、能正确命中控件。

**改法**：拖拽类交互改用 `run_script` **直接调真实方法**，走完整链路：

```gdscript
_card_ui.call("BeginPress", Vector2(660, 942))     # 按下
_card_ui.call("UpdateDrag", 0.016, Vector2(660, 700))  # 上移 242px
_card_ui.call("FinishDrag", true)                   # 松手出牌
```

实测：手牌从 8 张变 7 张 → 出牌链路正常。

**教训**

- **测试工具的输入通道要分清**：后台模式里「点」能用、「拖」不能用。
  测拖拽 / 长按 / 滑动手势时，先确认输入通道可用，否则会把「工具没生效」误判成「代码坏了」。
- **但 Godot 的 `Button` 在后台模式下也点不动** —— Button 的 `Pressed` 要靠**真实鼠标位置**在按下与松手之间匹配，
  而后台模式的鼠标位置根本不更新。
  → 测按钮逻辑用 `button.emit_signal("pressed")`（照样能验证「信号 → 处理函数 → 切场景」整条链路）；
  → 测 `Panel` / `Control` 自己实现的 `_GuiInput` 则**可以**用 `simulate_input`（它收的是原始输入事件）。
  两条通道别混。
- 调 C# 的**公开方法**在 GDScript 里用 `node.call("方法名", 参数)`；
  但 **C# 属性不是方法**（`IsDragReady` 这种 `call` 不到）—— 要读值就用 `node.get("属性名")`。


## 63. 长按和拖拽共用「按下」入口，要用移动容差把两者分开

**现象**：卡牌上要同时支持「**长按** → 放大详情」和「**拖拽** → 出牌」，
两者都从「按下」开始 —— 如果不区分，玩家按住不动想看详情，结果松手时把牌打出去了。

**做法**：用**移动容差**把两种意图分开（不是用时间）：

| 阶段 | 判定 | 结果 |
| :--: | :--- | :--: |
| 按下 | 计时开始（0.35s） | 进入「按住」 |
| 计时内**移动超过 8px** | 长按**作废** | 转为拖拽意图（出牌优先） |
| 计时到且**没怎么动** | 长按触发 | 就地放大详情，松手复原 |
| 松手时**没移动、也没长按** | 视为「点击」 | 打开卡牌详情界面 |

**教训**

- **同一个手势入口要挂多种意图时，用「位移容差」区分意图，用「时长」做兜底** ——
  纯时间判定会把「按住 → 拖 → 出牌」这套最常用的操作判成「长按」。
- 「点击」这种**没有位移的短按**天然和拖拽不冲突，可以安全地拿来触发「查看详情」。
- 长按触发后**提示文字要换**（我们是「继续上移，松手使用」→「松手还原」），
  否则提示会继续误导玩家去做另一个动作。


## 64. 先 `Setup` 后 `AddChild`：节点还没进树，里面的引用全是 null

**现象**（2026-10-24）：「角色一览」列表 13 项都渲染出来了，但每一项都是**默认文字**
（「角色」/「追击」），头像也没画上 —— 可 `Setup()` 里明明赋了值。

**根因**：写成了

```csharp
var item = itemScene.Instantiate<CharacterGalleryItem>();
item.Setup(character);      // ← 此时节点还没进场景树
_grid.AddChild(item);       // ← _Ready 在这之后才跑
```

`Setup()` 里要写 `NameLabel.Text`，得先拿到 Label 引用；而这些引用是在 **`_Ready()`** 里取的。
节点没 `AddChild` → `_Ready` 没跑 → 引用全是 `null` → **赋值被静默丢掉**（C# 里对 null 引用赋属性会抛异常，
但代码里写的是 `if (_nameLabel != null)` 的保护分支 → 什么也不发生）。

**改法**：**先 `AddChild` 再 `Setup`**（`_Ready` 跑完，引用就绪）：

```csharp
var item = itemScene.Instantiate<CharacterGalleryItem>();
_grid.AddChild(item);       // 先进树
item.Setup(character);      // 再填数据
```

**教训**

- **`Setup` / `Init` 类方法要在节点进树之后调用** —— 这是 Godot 的通用顺序，不是本项目特有。
- 症状是「**内容全是默认值**」而不是报错 → 先怀疑「引用没拿到」，
  而不是「数据没传进来」（本例数据其实是对的）。
- 配套：`TextureRect` 的 `expand_mode = IGNORE_SIZE` + `size_flags_horizontal = SHRINK_CENTER`
  会让它的**宽度被压成 0**（最小宽度被忽略）→ 贴图「加载了但看不见」。
  要固定尺寸就给**非零的 `custom_minimum_size`**（本例头像 120×120、卡面 88×92）。


## 65. 批量改写脚本要**逐条看 MISS 输出**，别只看「patched」

**现象**：用一次性脚本批量改三个文件，脚本最后打印「patched MainMenu.cs」，
但改完发现「角色一览」按钮点了没反应 —— 查源码才发现：**字段声明、`GetNode`、`Pressed +=` 三处都没打上**，
只有方法体进去了（编译还过，运行也不报错，只是按钮没反应）。

**根因**：脚本里同一批替换的**缩进假设不一致**（有的文件用 Tab、有的用 4 空格），
匹配不上的那几条被 `MISS` 打印了出来 —— 但那一屏输出里好几行 `MISS` 混在 `patched` 之间，
**扫一眼没注意到**。

**改法**：
1. 批量改写时，**逐条核对 MISS 行数 = 预期条数**；
2. 改完**回读文件**（`grep` 关键符号）确认每一处都真的落盘了；
3. 缩进不确定时，先 dump 几行看真实缩进（`node -e "…replace(/\t/g,'»')…"`）再写替换串。

**教训**

- 「脚本说成功」不等于「改动都在」—— 批量替换是**部分成功**的高发场景。
- **编译通过 ≠ 功能接线正确**：漏掉的可能是 `GetNode` 与信号连接这种
  「少一行就静默失效」的地方（参考 §59 的同类教训）。


## 66. 容器内容超出容器高度 → 溢出把整个布局顶出屏幕

**现象**（2026-10-24）：角色一览的「卡牌总览」里，左边那列 13 个角色头像
（每个 132px + 8px 间距 = 1812px）放进一个 1083px 高的 `VBoxContainer` ——
结果**整个视图往上顶飞了**：右侧的标题、大招面板、卡牌插画全跑到屏幕外，
只剩几行文字露在最上面。

**根因**：Godot 的 `BoxContainer` 在**内容超过容器**时不会裁剪，
而是把溢出量分摊到**两端**（等于内容被「居中」了）→ 上半截跑到屏幕外。
不是 bug，是**容器用错了**：固定长度的列表必须套 `ScrollContainer`。

**改法**：

```
CardsView/HBox
├── AvatarScroll (ScrollContainer)   ← 加这一层
│   └── AvatarColumn (VBoxContainer)
└── CardsSide (VBoxContainer)
```

**教训**

- **「一列 N 个重复项」= 先想滚动**。`VBoxContainer` / `HBoxContainer` 只适合**内容长度可控**的布局。
- 症状识别：内容**整体偏移**（不是被裁掉，而是跑到屏幕外）→ 基本都是容器溢出。
- 配套：另一个坑是**子项被拉伸** —— 容器里的项默认 `size_flags_vertical = FILL`，
  会被拉满整行高度（卡牌项被拉成 873px 高的小细条）。
  要按内容高度排就写 `size_flags_vertical = 4`（SHRINK_CENTER）。


## 67. ScrollContainer 刚填完内容时 `max_value` 还是 0，此刻设滚动位置无效

**现象**：竖列头像填好了，想把滚动条滚到当前选中的那个（13 个头像放不下一屏，
不滚就看不到高亮）—— 设了 `bar.Value` 但**纹丝不动**（读回来还是 0）。

**根因**：`ScrollContainer` 的滚动条范围是**布局排完才知道**的。
刚 `AddChild` 完还没排版，此时 `bar.MaxValue` 仍是 **0**，
于是 `Mathf.Clamp(value, 0, 0)` → **被夹成 0**。

**改法**：**延后一帧再设**（用一个待办标志，在 `_Process` 里执行）：

```csharp
private bool _pendingAvatarScroll = false;

public override void _Process(double delta)
{
    if (!_pendingAvatarScroll) return;
    _pendingAvatarScroll = false;
    ScrollAvatarColumnToCurrent();   // 此时布局已完成，max_value 正确
}
```

**教训**

- **凡是「读容器算出来的尺寸」都要等布局完成** —— 布局发生在 `NOTIFICATION_SORT_CHILDREN`，
  早于它读到的都是上一帧（或 0）的值。
- 症状识别：设了 `Value` 却**没报错、没效果、读回来是 0** → 典型的「被 clamp 成 0」。


## 68. 批量改 JSON 数据表要**保持原格式**，否则整份文件变成 diff

**现象**（2026-10-24）：用脚本给 `character_cards.json` 补 4 个字段，
结果 `git diff --stat` 显示 **757 增 745 删** —— 明明只加了 15 行。

**根因**：脚本用 `JSON.stringify(obj, null, 2)` 写回，而原文件是 **4 空格缩进**；
另外换行风格也要跟原文件一致（本仓库 `core.autocrlf=true`：**工作区 LF / blob CRLF**，
脚本要检测**当前文件**的换行风格再写回，不能想当然用 `\n`）。

**改法**：

```js
const raw = fs.readFileSync(p, 'utf8');
const crlf = raw.includes('\r\n');
const s = crlf ? raw.replace(/\r\n/g, '\n') : raw;   // 先统一成 LF 处理
// ...改数据...
let out = JSON.stringify(j, null, 4) + '\n';            // 缩进跟原文件一致
if (crlf) out = out.replace(/\n/g, '\r\n');             // 再还原换行风格
fs.writeFileSync(p, out, 'utf8');
```

**教训**

- **改数据表前先看原文件的缩进与换行**（`git show HEAD:<file> | head`）——
  写回时必须**逐字节复现**原格式，只改内容。
- 「757 增 745 删」这种量级一看就知道是**格式被重排**了，不是内容改动；
  先 `git checkout -- <file>` 撤销再修脚本，别在脏 diff 上继续改。


## 69. `[Export] List<string>` 不被 Godot 的 C# 绑定支持（GD0102）

**现象**：给 `Card` 加 `Affixes`（词缀数组）时顺手加了 `[Export]`，
编译直接报 `GD0102: The type of the exported member ... is not supported`。

**根因**：Godot 4 的 C# 绑定**不支持导出 `List<T>`**（只支持 `T[]`、
`Godot.Collections.Array<T>`、以及 Godot 内置类型）。

**改法**：去掉 `[Export]`，当普通属性用（运行时从 JSON 填，编辑器里看不到也无所谓）——
本项目里 `Card.EffectIds` 早就是同样写法。

**教训**

- **给已有类加集合属性前先看同项目的先例**（本项目 `EffectIds` 没加 `[Export]`），
  照抄比试错快。
- 报错信息里带 `GD0102` 的都是**编辑器绑定层**的限制，不是 C# 语法问题 ——
  改用数组或去掉 `[Export]` 即可。
