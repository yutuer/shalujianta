校验器（`tools/check-task-stats.ps1`）要靠正则读 markdown 表格，有两处必须注意，否则会出现"文档明明对，脚本却报漂移"：

**坑一：ID 带了 markdown 强调符号**。总表里想把重点行加粗，写成 `| **D12** | ... |`，脚本按原始字符串比对就找不到对应标题，报「逐项展开缺对应标题」。
**修法**：比对前**归一化**，剥掉 `*` `` ` `` `~`：

```powershell
$id = ($cells[1].Trim() -replace '[\*`~]', '')
```

**坑二：状态标记不在行尾**。脚本靠 `^(###\s*(D\d+)\s*·.*?)(状态)\s*$` 定位展开章节，标题末尾必须是状态标记。
写 `### D12 · 地图多簇生成 ⬜ 🔺 **最高难度**` 会匹配失败——`⬜` 后面还有东西，`\s*$` 不成立。
**修法**：**状态标记永远放标题最后**，其他标记（难度、警告）放它前面。

> 两条都踩过：加粗 D12 后校验器立刻报「缺对应标题」，一度以为是总表写错。**校验器报错先怀疑脚本的容错，再怀疑文档**——但也要确认脚本没因此漏检（改完务必做一次反向测试）。

## 2. `.tscn` 是布局的唯一真相

`SilverKeyProgressIndicator.cs` 找 `ValueLabel` / `MaxLabel`，但 `.tscn` 里它们嵌在 `VBoxContainer` 下 → 每次进地图报 2 次 `Node not found`，而且**银钥圈里的数字从来没显示过**。

## 3. C# ↔ GDScript 桥接限制

调试时会撞墙的三条：

- C# 属性不加 `[Export]` → **GDScript 读不到**（`get("CurrentMap")` 返回 null）
- C# 的 public 方法 → **GDScript 也调不到**（`call("GetSavedMap")` 报 `Nonexistent function`）
- `.tscn` 里 Control 的位置存的是 `offset_left/offset_top`，不是 `position`

**教训**：跨语言调试要么写 C# 侧代码，要么改用 Godot 原生 API（`Label.text`、`Control.mouse_filter`、`Node.is_processing_input` 等）去观察。

## 4. 无头 / 后台窗口里模拟点击不可靠

godot-runtime MCP 的 `run_project(background: true)` 把窗口放在**屏幕外 `(-9999,-9999)`**，`Control.GetLocalMousePosition()` 读的是**真实 OS 光标**位置，合成事件改不了它 → 任何"点击命中某控件"的代码路径都测不到。

`HexTileView` 正是用 `GetLocalMousePosition()` 判断点击是否落在格子内。

**可行的替代**：写一个**临时 C# 集成测试**（临时注册成 autoload 以跨场景存活），由 C# 直接调游戏自己的 API 驱动流程，断言结果写进 `user://` 文件；测完把 autoload 注册和测试文件一并删掉。2026-10-20 用这招跑通了 24 项断言。

## 5. `git push` 会上传大文件

push 传输的是「**远端缺失的对象**」，不是增量 diff。若某个待推送提交引入了大文件而远端还没有，push 会真把那些 blob 传上去（实测 2.4GB 传了 4 分钟还没完），**哪怕下一个提交就删了它们**。

**正确做法**：先改写**从未推送过的**本地历史再推：

```powershell
git filter-repo --force --path <路径> --invert-paths --refs <远端SHA>..HEAD
```

只改写远端没有的提交，**不影响已推送历史，无需 force push**。

配套：改写后要清掉 IDE 留的记账引用（Trae 的 `refs/trae_merge/*`，用 `git update-ref -d <ref>`），再 `git reflog expire --expire=now --all` + `git gc --prune=now` 才会真正回收磁盘空间。

**现在怎么做**：导出产物（`dabao/`、`qianye.*`、`*.tpz`、`*.rar`）、`.godot/`、`.mcp/`、原始参考图 PNG 都已在 `.gitignore` 里；参考图入库前先压到 3.2MB 再推。

## 8. `.tscn` 根节点漏绑 script → 组件静默退化成空节点

2026-10-20 在战斗场景排查报错时发现：`AttackerDisplayUI.tscn`、`RageDisplayUI.tscn`、`KeyOrderSelectionUI.tscn` **三个场景的根节点都没有 `script = ExtResource(...)`**（ext_resource 声明了脚本，但没挂到根节点上）。

后果很隐蔽：`BattleManager.LoadUIComponent<T>()` 里的 `packedScene.Instantiate<T>()` 因为类型不匹配返回 null，于是走**代码兜底** `new T()` —— 得到一个**没有任何子节点的空 Control**。于是运行日志里出现：

```
[BattleManager] 攻击体角色显示UI初始化成功      ← 看着像成功
ERROR: Node not found: "VBoxContainer/TeamStatsLabel"   ← 其实是空节点
```

**攻击体编队、怒气槽、钥令选择这三个 UI 实际上一直是空的**，只是没有崩所以没人发现。修法就是在根节点补一行 `script = ExtResource("1")`。

**教训**：

- 新建 `.tscn` 时，**根节点一定要绑脚本** —— 只声明 ext_resource 不等于挂上了
- 「从场景加载: xxx.tscn」这条日志是组件是否真的走了场景路径的判据；缺它就说明退回了代码兜底
- 一键排查：`Scenes/**/*.tscn` 里凡是有 Script ext_resource 的，根节点都要有 `script =`

## 10. 子节点也要挂脚本，且一个 .cs 只能一个类

接 §8：修好根节点的 script 之后，`AttackerDisplayUI` / `RageDisplayUI` 虽然能加载了，但它们的 **4 个槽位节点（`CharacterSlot0..3` / `RageSlot0..3`）还是空 Panel**，日志报「未找到角色槽位节点」。原因有两层：

1. 槽位节点也没挂脚本 → `GetNode<Panel>(path) as CharacterSlotUI` 得到 null
2. **`CharacterSlotUI` / `RageSlotUI` 原本和宿主类写在同一个 .cs 文件里**（Godot 一个脚本文件只能对应一个类，`.tscn` 挂脚本时按文件绑定），必须先拆成 `Scripts/UI/CharacterSlotUI.cs` / `Scripts/UI/RageSlotUI.cs` 再挂

另外 `RageDisplayUI` 的槽位路径本身也写错了：实际是 `VBoxContainer/RageSlotsContainer/RageSlotN`，代码写的是 `RageSlotsContainer/RageSlotN`（少一层）。修正前 UI 显示的是 `.tscn` 里的静态占位文字「怒气值 0/100 0/100…」，修正后才显示「鼠 0/100 0%　牛…　虎…　兔…」+「总怒气 0」。

**教训**：新建带子组件的 UI 场景时，**每个需要脚本的节点都要单独挂脚本，且对应独立的 .cs 文件**；写完用 `HasNode(path)` 验证过的路径去取，取不到时 Godot 只报「未找到」不崩，很容易被忽略。

## 11. 血条初始值需要手动推一次

`HexMapUI` 只在 `OnHealthChanged` 事件里更新血条，但 `HexMapController` 比 `HexMapUI` **先**就绪，初始那次事件早于订阅，**不会被补发** —— 所以血条一直显示 `.tscn` 里的默认值 100/100，跟队伍总血量（125）毫无关系。修法是在订阅后手动推一次：

```csharp
_healthBar?.SetHealth(_controller.PlayerCurrentHealth, _controller.PlayerMaxHealth);
```

**教训**：跨节点的"初始状态同步"不会自动发生，凡是 UI 靠事件驱动的值，都要在订阅后手动同步一次。

## 12. 用 Agent 跑测试时的提交陷阱

`godot-runtime` MCP 启动项目时会**往 `project.godot` 的 `[autoload]` 注入一行**：

```ini
McpBridge="*res://.mcp/godot-runtime/bridge/mcp_bridge.gd"
```

测试会话运行期间 `git status` 会显示 `M project.godot`（**这是正常的**），停止/关闭项目后会自动还原。

**但如果你在会话运行期间执行 `git add .` 或 `git commit -a`**，这行会被提交进仓库 —— 而 `.mcp/` 本身是 gitignore 的，别人克隆后这条 autoload 指向不存在的脚本，**项目直接启动失败**。

**规矩**：跑测试期间只 `git add` 具体文件；确认 `project.godot` 没有意外改动再提交。

## 13. PowerShell 脚本的 UTF-8 BOM

**（2026-10-20）** 用文件写入工具新建 `.ps1` 通常写成**无 BOM**，PowerShell 5.1 读它时把中文当 ANSI 解析成乱码。

关键在于**乱码会连累参数解析**，报出的错误完全看不出是编码问题：

```
A positional parameter cannot be found that accepts argument '*.png -File | Sort-Object Name'
```

这个报错看起来像脚本逻辑写错，实际是编码问题。**排查顺序**：先查文件头三字节是不是 `239,187,191`（UTF-8 BOM），再怀疑逻辑。

补 BOM 的做法（不依赖编辑器）：

```powershell
$p = 'tools\convert-reference-images.ps1'
$txt = [System.IO.File]::ReadAllText($p, [Text.Encoding]::UTF8)
[System.IO.File]::WriteAllText($p, $txt, (New-Object Text.UTF8Encoding $true))
```

**用编辑工具改已有的 .ps1 一般不会丢 BOM**（BOM 在文件首字节，替换的是中段内容），但**新建文件会**。改完一律用首三字节核对，别等跑报错。

## 14. PowerShell 里 `gh --jq` 表达式会被拆词

```powershell
gh api repos/yutuer/shalujianta/contents/docs --jq '.[] | "\(.name)  \(.size)"'
```

在 PS 5.1 下会被拆成多个参数，报 `accepts 1 arg(s), received 3` 或 `failed to parse jq expression`。

**改法**：让 gh 只吐 JSON，自己格式化：

```powershell
$items = (& $gh api repos/yutuer/shalujianta/contents/docs) | ConvertFrom-Json
$items | ForEach-Object { "{0,-42} {1,8} B" -f $_.name, $_.size }
```

## 15. 批量压图不必装 ImageMagick

要把大图入库时，Windows 上 PowerShell 5.1 自带的 **GDI+（System.Drawing）** 就够：

```powershell
Add-Type -AssemblyName System.Drawing
# Image.FromFile → 按比例算新尺寸 → Graphics.DrawImage
#   配 InterpolationMode=HighQualityBicubic
# → 存 JPEG 用 ImageCodecInfo 找 'image/jpeg' 编码器
#   + EncoderParameter(Encoder.Quality, 88)
```

实测（2026-10-20）：14 张 2562×1400 PNG，29.8MB → 1920 宽 JPG **3.19MB**，画质足够读清界面小字，GitHub 仓库从 32MB 变 1.3MB。

可复用脚本：[`tools/convert-reference-images.ps1`](../tools/convert-reference-images.ps1)（幂等，重复跑不会重复转）。

**注意**：`System.Drawing` 只在 .NET Framework（PS 5.1）里有，PowerShell 7 / .NET Core 需另装 `System.Drawing.Common`。原图别删，移到 gitignore 的子目录本地备查。

## 17. 术语/结论会随模型演进而过期

本项目的地图模型在一天内被推翻了三次（「簇只由洞产生」→「簇有两个来源」；「三层结构」→「四层」；
「洞 = 桥」→ 洞是**顶点**、要判断的是**割点**）。**文档里的术语一旦落后于模型，读者就会按错的模型理解代码。**

2026-10-20 的回读测试抓出三类问题：

| 类型 | 例子 | 修法 |
|---|---|---|
| **术语错误** | 把「洞」写成「桥（cut edge）」—— 洞是格子（顶点），消耗后消失，要判断的是**割点（articulation point）** | 术语写错比不写更危险，直接改 |
| **旧称残留** | 「桥树」与引入传送门/单向门后的「簇图」混用 | 统一改称；旧称只允许出现在**术语纠正段**里做对照 |
| **结论过期** | 早期条目说「簇只由洞消耗产生」 | 变更记录表**上方加「以最新条目为准」说明**，并列出被推翻的结论 |

**教训**
- 早期条目不是垃圾，是**当时的真实结论**；但必须标注它已被修正，否则会被误读成现状
- 回读测试要**固化成脚本**，不能靠人记得做 → `tools/check-doc-consistency.ps1`

**顺带一个 PowerShell 坑**：`[System.IO.File]::WriteAllLines()` 在 Windows 上默认写 **CRLF**，
会把原本 LF 的文件整体转成 CRLF——之后 `edit` 工具的所有多行匹配全部失败（LF 与 CRLF 不匹配），
排查方向容易跑偏。用 `WriteAllText()` 保留原换行，或写完统一 `Replace("`r`n","`n")`。

## 19. 「地图完成」这个状态没有落到数据层

六边形地图模式下，地图完成的链路是：

```
BattleTransitionManager.PendingMapCompletion（标记）
  → 回地图 → HexMapController.RestoreMapState() 读到标记
  → 打印「BOSS 已击败，结算地图完成」→ CompleteMap()
  → 只发 OnMapCompleted 事件 + 清存档
```

问题：
- `MapManager.CompleteMap()`（设置 `_isMapCompleted`）**根本没被调用** → `MapManager.IsMapCompleted()` 在六边形地图模式下**恒为 false**
- `MapDefinition.IsCompleted` 也没被设置
- 也就是说：**「这张地图打完了」这个事实没有任何地方存着**

影响：以后要做「地图选择 / 关卡进度 / 存档」时，得先补一个可查询的完成状态。

**教训**：写「完成 / 失败」这类**状态**时，要明确它落在**哪个数据对象**上。
只有事件和日志是不够的 —— 事件会随场景一起销毁，测试也断言不了。

## 20. 文档标题里的状态标记必须放行尾

`tools/check-task-stats.ps1`（以及 `check-doc-consistency.ps1`）用这个正则定位「逐项展开」的章节标题：

```
^(###\s*(D\d+)\s*·.*?)(状态标记)\s*$
```

**状态标记必须是标题的最后一个东西**。写成这样会匹配失败：

```
### D4 · 战斗胜利结算界面 ✅ **已完成**     ← ❌ 标记在中间
```

必须写成：

```
### D4 · 战斗胜利结算界面 **已完成** ✅     ← ✅ 标记在行尾
```

报错信息是「开发计划条目 [D4] 在需求池总表有，但逐项展开缺对应标题」——
**看起来像标题写错了，其实是标记位置不对**，容易误判。

**教训**：写完条目标题，习惯性把状态标记放到最后；改完跑一次 `check-doc-consistency.ps1` 就能立刻发现。

（这个坑今天在 D4 和 D1 上各踩了一次，都是校验器当场报出来的。）

## 21. 一次性事件的类型，在触发回调之前就被清空了

D5 做探照灯时踩的。

`HexTile.Trigger()` 的流程是：**先**把 `EventType` 清成 `Empty`（一次性事件用完即焚），**再**发出 `OnTileTriggered` 回调。

所以在 `OnTileTriggered` 里读 `tile.EventType` 拿到的永远是 `Empty` —— 探照灯认不出来，弹窗不出现。

[HexMapUI] OnMapEventTriggered: searchlight @ (-1, 2)        ← 换个订阅点就对了

**教训**：订阅格子事件时，先问一句「这个回调拿到的数据还是原始的吗」。
凡是「用完即焚」的状态（一次性事件、消耗型道具），**清理动作要放在回调之后**，否则订阅方永远看不到它。

## 22. 「存了但从来没被读过」= 死代码

D5 的 1.9.5「已照亮集合进地图存档并恢复」—— 我先写了存档端（`BattleTransitionManager.SaveRevealedTiles`），

**教训**：写「持久化」这类需求时，**必须能说出「谁在什么时候读它」**。
写完把方法名 grep 一遍，确认有调用点；没有就是半成品。

## 24. 手写的 `uid://xxx` 不是 Godot 的合法 UID，每次加载都刷警告

在 `.tscn` 里手写场景引用时，我习惯给每个资源加一个「好认的」 uid：

```
[ext_resource type="PackedScene" uid="uid://scorepanel" path="res://Scenes/UI/ScorePanel.tscn" id="7_scorepanel"]
```

Godot 的 UID 是 **base31 编码**的短字符串（形如 `uid://dhynr33kc8wor`），
`scorepanel` 这种带小写明文的串**解不出来**，于是每次加载场景都会刷：

```
WARNING: res://Scenes/UI/HexMapUI.tscn:9 - ext_resource, invalid UID: uid://scorepanel
         - using text path instead: res://Scenes/UI/ScorePanel.tscn
```

功能上是没问题的（Godot 会退回用 path 匹配），但**每次启动都刷警告**，
真正出问题时警告就被淹没了。

**修法**：新写的 `.tscn` **不要手写 uid**，只写 `path`；
根节点的 `uid="uid://..."` 也一并去掉，让 Godot 自己在编辑器里保存时分配。

**教训**：Godot 资源文件里看起来「像格式」的自造值不一定合法。
手写配置时优先用**最朴素的合法形式**（path 而非 uid），让工具自己补全那些需要唯一标识的字段。

## 25. 「取不到就跳过」的写法，会把配置错误藏起来

D3 做关卡详情弹窗时，敌方预览和奖励预览的图标**一片空白**，但代码里没有任何报错。

原因是我在 slot 里这样取节点：

```csharp
_icon = GetNodeOrNull<TextureRect>("Icon");   // ← 实际路径是 "Frame/Icon"
```

`GetNodeOrNull` 取不到就返回 `null`，而我的代码是「取不到 → 隐藏图标」，于是**看起来像「资源不存在」**，
实际上是我把路径写错了 —— `Icon` 在 `Frame` 下面，不是 slot 的直接子节点。

同时还叠加了第二个错误：图标路径 `res://Assets/Icons/enemy.png` **这个文件根本不存在**
（项目里只有 `enemy_elite.svg` / `enemy_cultist.svg` / `skull.svg`）。

**两个错误叠在一起，表现完全一样：一片空白。**

**修法**
1. 路径改成 `Frame/Icon`
2. 敌人图标映射到**实际存在**的资源：BOSS → `skull.svg`、精英 → `enemy_elite.svg`、普通 → `enemy_cultist.svg`
3. 顺手把 `HexMapGenerator` 里指向不存在 png 的 9 个 `IconPath` 修了三个，
   并让 `HexTileView` 真正读 `IconPath`（文件不存在才回退到文字符号）

**教训**

- **`GetNodeOrNull` 返回 null 时，不要静默跳过** —— 至少打一条 `GD.PrintErr`，
  否则「我写错了路径」和「资源不存在」会被当成同一件事。
- **引用资源前先确认它存在**：`ResourceLoader.Exists(path)` 先判一次，
  或者写完路径后 glob 一遍资源目录确认文件名。
- **「界面空白」类的 bug，先怀疑路径，再怀疑资源，最后才怀疑渲染逻辑** —— 顺序反了会浪费很多时间。

## 26. 两个 Godot / C# 的语法与样式陷阱

D10 改关卡展示页时连踩两个，都不报错、只是「不生效」。

### 陷阱一：`?.Pressed += ...` 是 C# 14 特性

```csharp
_prevButton?.Pressed += () => SwitchChapter(-1);   // ← CS9202
```

「null 条件**赋值**」是 C# 14 才有的，项目是 C# 12 → 编译直接报错：

```
error CS9202: 功能"null 条件赋值"在 C# 12.0 中不可用。请使用语言版本 14.0 或更高版本。
```

**正确写法**：

```csharp
if (_prevButton != null) _prevButton.Pressed += () => SwitchChapter(-1);
```

> 注意区分：`?.Pressed`（读，安全）和 `?.Pressed +=`（赋值，C# 14）。
> 事件订阅一律用 `if` 判空。

### 陷阱二：PanelContainer 的内边距要配在 stylebox 上

想在卡片里留白，写成主题常量**不生效**：

```ini
theme_override_constants/content_margin_left = 18   # ← 无效，内容照样贴边
```

`PanelContainer` 的内容内边距来自 **panel stylebox 的 `content_margin_*`**，
要么改 StyleBoxFlat 的属性，要么用 `AddThemeStyleboxOverride` 在代码里设。

**正确写法**（写进 `.tscn` 的 sub_resource）：

```ini
[sub_resource type="StyleBoxFlat" id="StyleBoxFlat_card"]
content_margin_left = 18.0
content_margin_top = 12.0
content_margin_right = 18.0
content_margin_bottom = 12.0
```

**教训**：Godot 的「主题常量」和「样式里的属性」是两套东西，
**内边距/圆角/描边这类都住在 StyleBox 里**。
改样式没生效时，先确认改的是不是同一个地方 —— 跟 D3 的 `GetNodeOrNull` 路径问题一样，
**「静默不生效」比「报错」更难查**。

## 27. 弹窗每次打开都 `+=` 事件 → 点一次确认触发两次

D11 给商店加刷新二次确认时踩的。

最初的写法是**每次点「刷新」都订阅一次**：

```csharp
private void OnRefreshPressed()
{
    var dialog = GetOrCreateConfirmDialog();
    dialog.OnConfirm += DoRefresh;        // ← 每点一次刷新就多一个订阅者
    dialog.OnCancel += OnRefreshCancelled;
    dialog.ShowConfirm("确认刷新", "……");
}
```

看起来没问题（弹窗是复用的），但**事件不会自动清空**：
- 第 1 次点刷新 → 订阅 1 个 → 点「取消」，不触发刷新 ✓
- 第 2 次点刷新 → 订阅成 2 个 → 点「确认」→ `DoRefresh` 执行 **2 次** → **多扣一次黑印**

测试直接抓到了：断言「确认后刷新触发次数 == 1」，实际是 2。

**修法**：订阅放在**创建时**，不是每次显示时：

```csharp
_confirmDialog = _confirmDialogScene.Instantiate<ConfirmDialog>();
AddChild(_confirmDialog);
_confirmDialog.OnConfirm += DoRefresh;      // 只订阅这一次
_confirmDialog.OnCancel += OnRefreshCancelled;
```

**教训**

- **事件订阅要放在「生命周期开始」的位置**（创建 / `_Ready`），
  不要放在「每次显示」的位置 —— 后者会累积订阅者。
- 万一不得不重复订阅，就**先 `-=` 再 `+=`**。
- 这类 bug **不报错、只多点一次**，靠人眼点两下是发现不了的 ——
  **断言里要写死调用次数**（「触发次数 == 1」而不是「触发了」）。

顺带记一个同源的坑：**弹窗被下层内容盖住**。
光靠「后添加的节点画在上面」不总成立（地图格子的 `Line2D` 就盖过商店面板），
弹窗这类要显式设 `z_index`（`ShopUI` = 50，`ConfirmDialog` = 100）。

## 28. 主题里改尺寸 = 把既有布局挤爆

D2 做统一主题时踩的。

第一版 `MainTheme.tres` 里给按钮的 stylebox 设了内边距、还把默认字号调大：

```ini
content_margin_left = 18.0
content_margin_top = 8.0
...
default_font_size = 18
```

结果**关卡页右下角的两个按钮被挤出容器、叠在一起**（截图才看得出来）。

原因：Godot 容器（HBox / VBox）按子控件的**最小尺寸 + size_flags** 分配空间。
主题一旦改了控件的最小尺寸，**所有没重新算过的布局都会跟着变** ——
而项目里几十个 `.tscn` 的尺寸是各自手写的，没人算过主题的影响。

**修法：主题只负责「颜色与描边」，尺寸一律不管**

```ini
; 注意：这里**只定义颜色与边框**，不设 content_margin、不改 default_font_size ——
; 一旦改动控件尺寸，现有线框布局（按钮并排、HBox 排列）就会被挤爆。
```

改完立刻所有布局恢复原样，而底色/金线/字体色照样统一。

**教训**

- **Theme 优先只放「颜色 + 描边 + 字体」**，别碰 `content_margin` / `default_font_size` ——
  这两个是**尺寸**，会传导到所有容器的布局计算里。
- 真要统一尺寸，先在**一个**场景试，确认不炸再铺开。
- **改了主题必须截图看布局**，不能只看「主题加载成功」的断言 ——
  这次就是靠截图才发现按钮被挤爆的。

## 29. 测试用例的建模错误，会伪装成「算法有 bug」

D13 做地图校验器时，6 个断言挂了 —— 看起来像算法写错了。

**实际错的是测试用例本身**，三个坑叠在一起：

### 坑一：`End` 和 `required` 撞在同一个节点

```
节点 3 既是终点（End）又是必经格（required）
```

于是「访问到 required」就等于「到达终点」→ 死锁用例根本不成立，
状态空间正常返回 `CanComplete = true`，**算法被判死刑**。

### 坑二：`Normal` 表示「双向」，但用例只加了一个方向

玩具图里 `Connect(0, 1, Normal)` 只往邻接表里塞了 `0 → 1`。
可缩簇逻辑是按 `kind` 判断的 —— `Normal` 就算连接边 → `0` 和 `1` 被合并成一个簇。
**于是「簇」和「实际可达性」自相矛盾**，后面的判定全歪。

修法：`kind != OneWay` 时**自动补反向边**。

### 坑三：旁支用例把终点放在了旁支簇里

「拐进旁支就回不来」要成立的前提是**终点在起点那一侧**。
我把终点也放进了旁支簇 → 玩家拐进去照样能到终点 → **本来就不该报警**。

### 教训

- **写反向用例时，先用一句话说清「玩家在这里会怎样」，再动手画图。**
  图画完先自己走一遍（玩家从 S 出发能不能通关？required 在哪一侧？终点在哪一侧？）。
- **断言失败时，先怀疑用例，再怀疑实现** —— 尤其当多个用例同时失败、且失败模式很「整齐」时，
  通常是共用的建模假设错了，而不是算法错了。
- 调试手段：**把报告完整打出来**（`report.ToString()`）。
  D13 这次就是靠打印看出「簇 2、起点可达 4、能到终点 2」，
  立刻明白终点落在了旁支侧 —— 一眼看穿用例的错。

## 30. 「对」和「个」的口径不一致，配额永远差一倍

D14 做关卡配额时踩的。

规格里传送门写的是**「对数」**（`teleportOneWay: 1` = 1 对门），
但核对配额时我按**「格子数」**去比：

```
期望 1 个单向门格，实际 2 个   ← FAIL
```

原因：**每对传送门占 2 个格子**（入口 + 出口）。单向门、双向门都一样。

**修法**：把两个口径在代码里分开命名，不留模糊地带：

```csharp
/// <summary>单向门<strong>对数</strong>（每对占 2 个格子）</summary>
public int TeleportOneWay;

/// <summary>传送门占用的格子总数（每对 2 格）</summary>
public int TeleportTileCount => (TeleportOneWay + TeleportTwoWay) * 2;
```

配额核对、可满足性检查、测试断言三处全部改成用 `TeleportTileCount` 换算。

**教训**

- **配置里凡是「成对出现」的东西，都要明确写清楚单位**（对 / 个 / 格），
  并提供一个换算属性，别让每个调用点自己乘 2。
- **配额类数据最容易被「差一倍」坑到**：一个映射写反了，所有数量断言全错。
  写完先手算一遍最小的例子（1 对门 = 2 格）再往下写。

## 31. 「洞」在两处判定里的含义不一样，混用会导致永远判不出割点

D12 做洞消耗分裂时踩得最深的一个坑。

洞是**消耗型节点**，在两个地方含义完全不同：

| 场景 | 洞算不算连接边 | 问的是什么 |
|---|---|---|
| 判定「洞是不是割点」 | **算**（洞是普通可走格） | 洞**还在**的时候，它是不是连接两块的关键 |
| D13 的簇图分析 | **不算**（用掉即断） | 洞**已消耗**之后，地图还怎么连 |

我一开始用 D13 的 `ClusterGraphAnalyzer` 判割点，结果是：

```
洞候选 (6, 8) 不是割点（分量 2 -> 2）
洞候选 (6, 3) 不是割点（分量 2 -> 2）
... 93 个候选全部「不是割点」
```

原因很直白：`ClusterGraphAnalyzer` 缩簇时会**移除所有洞**，
所以「移除某个洞之后的图」和「完整图」在它眼里**一模一样** → 分量数永远相等 → 永远不是割点。

**修法**：判割点时用**纯邻接边**算连通分量（洞当普通格），
「移除该洞后分量数增加」= 它是割点。

**教训**

- **同一个概念在不同上下文里含义可能不同** —— 借用现成工具前先问一句「它对这个东西的处理是不是我要的」。
- **「移除前后没区别」是个强信号**：如果两个输入总是得到同样的结果，
  说明其中一个输入根本没起作用（这里就是洞被提前移除了）。
- 写这类判定时，**在注释里写清「这里洞算不算边」**，比事后靠 debug 打印快得多。

## 32. 随机游走长出来的图里没有割点

D12 要做「洞消耗后簇分裂」→ 洞必须是**割点**（删掉它，两块区域才真的断开）。

但簇是「随机游走生长」出来的 —— 游走会绕圈，簇内部**全是环**：

```
洞候选 (6, 8) 不是割点（分量 2 -> 2）
洞候选 (6, 3) 不是割点（分量 2 -> 2）
... 93 个候选，一个割点都没有
```

随机游走产生的图天然没有割点（每个点都有环上的替代路径），
所以「在块状区域里挖个洞」**永远不会让地图分裂**。

**修法：显式造出「窄口」**

```
[ 第一块子区域 ] —— [ 窄口 ] —— [ 第二块子区域 ]
```

第二块子区域的格子**不允许与第一块直接相邻**（只能通过窄口连），
于是窄口必然是割点 → 洞放在窄口上 → 消耗后这一簇真的裂成两块。

**教训**

- **要某个图论性质，就必须按那个性质去构造**，不能指望随机生成自然长出来。
  （要树就长树，要割点就留窄口）
- 随机游走 / 随机填充出来的结构，往往**恰好缺少**你需要的性质 ——
  随机不等于满足约束。

## 33. 「写了但没接线」—— 代码齐了，效果是零

D15~D19 这轮的核心发现：**五组功能全都是「骨架写了但没接线」的半成品**，
从代码上看每一处都存在、每一处都有完整实现，但**实际一个效果都没发生**。

| 组 | 看起来有 | 实际上 |
| :--- | :--- | :--- |

ew 一遍，

## 34. 减益「挂了却毫无作用」—— 三个独立的失效原因

D19 做敌人侧状态图标时发现：减益图标画出来了，但**实际数值一点没变**。
查下来是**三个各自独立的失效原因**，任何一个单独存在都足以让减益变成纯装饰。

**原因一：靠改属性值实现，对「属性本来就是 0」的目标完全无效**

`csharp
// DefenseDownDebuff 原来的写法
target.Defense = Mathf.Max(0, target.Defense - DefenseReduction);  // 防御 0 - 10 → 还是 0
`

敌人防御本来就是 0（
ormal_wave 三个敌人：守卫 DEF=2 / 游兵 DEF=1 / 斥候 DEF=0），
**破甲对斥候等于没打**。
**修法**：减益改为**参与伤害计算**（ModifyDamageEnemy），而不是改属性值 ——
破甲 = 「受到伤害 +N%」，对任何敌人都成立。

**原因二：靠 _owner 判定归属，但没人调 SetOwner**

`csharp
// VulnerableDebuff 原来的写法
if (defender == GetOwner()) { ... }   // GetOwner() 恒为 null → 判定恒不成立
`

Enemy.AddStatusEffect **从不调用 SetOwner** → _owner 永远是 null →
**易伤从来没生效过**（大招「龙王咆哮」的毒+易伤因此打不出来）。
**修法**：改成不依赖 owner —— 易伤总是施加给承受伤害的那个敌人自己。

**原因三：减益根本没进伤害计算流程**

`csharp
// Enemy.TakeDamage 原来的写法
int actualDamage = CombatCalculator.CalculateDamage(damage, Defense);
CurrentHealth = Mathf.Max(0, CurrentHealth - actualDamage);   // 减益被跳过了
`

CalculateModifiedDamage 存在却没被调用 → 减益只影响**图标**，不影响**数值**。
**修法**：TakeDamage 里补上 CalculateModifiedDamage。

**教训**

- **状态图标正常显示 ≠ 状态生效**。要给减益写断言时，
  要断言**数值变化**（「受伤 55 而非 50」），不能只断言「图标出现了」。
- 「挂上去没反应」优先查三件事：**属性值是不是本来就是 0**、
  **判定依赖的字段有没有被赋值**、**这个状态有没有进到最终计算里**。

## 35. 同一方法被调用方和执行方各记一次账

钥令「每回合 2 次」的上限，实际只能用 1 次。

`
第 1 次使用 → ApplyKeyOrderEffect 内部记 1 次 → 调用方又记 1 次 → 计数 = 2
             → CanUseKeyOrder() 变成 false → 第 2 次直接被拒
`

**双重记账**是这类「计数器」最隐蔽的失效方式：
- 代码看起来完全正常（两处都有记录，都很合理）
- 表现是「限额比预期少一半」，很容易被当成「数值配错了」
- 但 MaxKeyOrderUsePerTurn = 2 和实际只能用 1 次之间的**倍数关系**
  才是真正的线索 —— **如果限额是 3 却只能用 1 次，就不是倍数问题**。

**修法**：计数**只在执行者（管理器）里记一次**，调用方不再重复记录；
并且让管理器**自己守门**（超限直接拒绝 + 返回 ool），
这样「超限」在任何调用路径下都不可能被绕过。

**顺带**：计数器还可能**越界**（外部误调用导致计数超上限），
GetRemainingKeyOrderUses() 这类「剩余量」接口要**钳制到 0**，不能返回负数。

## 36. 改了实现就要改文案 —— 口径漂移会让玩家学错规则

D19 把「破甲」从「降低防御值」改成「受到伤害 +N%」（因为前者对防御为 0 的敌人完全无效，见 §34）。

## 37. QueueFree 是延迟删除 —— 旧按钮会叠在新按钮上面

D7 的通用事件弹窗（EventDialog）第二次打开时，**点选项没反应、面板也关不掉**。

根因在 BuildOptions：

`csharp
foreach (Node child in _optionBox.GetChildren())
{
    child.QueueFree();      // ← 延迟删除：本帧结束前旧按钮还在容器里
}
`

QueueFree 不是立刻移除节点，而是**标记删除、等本帧结束才真正释放**。
于是第二次 ShowEvent 时：

`
第一次打开 → 容器里 2 个按钮
第二次打开 → QueueFree 标记旧 2 个（但还在）→ 又 AddChild 新 2 个
           → 容器里实际有 4 个按钮：新 2 个在下面，旧 2 个在上面
`

**玩家点到的是上面那两个旧的** —— 它们已被标记删除、但还没释放 →
点击事件不生效 → 看起来就是「点了没反应」；而新按钮被压在下面 →
面板看着"卡住"关不掉。

**修法**：先 RemoveChild 立即摘除，再 QueueFree 释放：

`csharp
foreach (Node child in _optionBox.GetChildren())
{
    _optionBox.RemoveChild(child);   // 立即从容器里摘掉
    child.QueueFree();               // 再释放
}
`

**教训**

- **QueueFree 不等于「马上消失」**。凡是「清空容器再重建」的地方，
  只写 QueueFree 就会**旧新并存**。ShopUI 早就用过 RemoveChild + QueueFree
  （见 §27「RemoveChild 替代 QueueFree」），这次同一个坑在 EventDialog 又踩了一遍。
- **症状会伪装成别的问题**：这里的现象是「按钮点了没反应」，
  很容易被怀疑成「事件回调没接上」或「状态机卡住」，
  实际上问题在**渲染层**（按钮重叠）。
  排查这类「点了没反应」时，**先打印容器里的子节点数量**——
  数量对不上就说明是重叠，不是逻辑。
- **验证要覆盖「重复打开」**：只测一次打开，永远发现不了这个问题。
  本轮的断言就是「第二次打开仍是 2 个按钮」「连开 5 次不堆积」。

## 38. 无 viewBox 的 SVG 会被 Godot 导入成 512×512 空画布

4 个图标（	eleport_entry / 	eleport_exit / skull / rrow_reserve）
的 SVG **没有 width / height / iewBox**，只有一段 path 坐标（范围约 ±31）。

Godot 导入这类 SVG 时拿不到尺寸信息 → 按**默认 512×512 画布**导入 →
path 只占画布中心一小块 → 图形被缩到很小、或者在某些容器里显示异常。

对照项目里正常的图标（intent_attack.svg）：

`xml
<svg xmlns="http://www.w3.org/2000/svg" width="128" height="128" viewBox="0 0 128 128">
`

**修法**：给每个 SVG 补上 width / height / iewBox，viewBox 按 path 的实际
坐标范围给（如 -32 -32 64 64），导入后就贴合图形实际范围了
（现在传送门图标是 61×54 / 54×60，而不是 512×512）。

**教训**

- **SVG 必须有 iewBox**，否则尺寸由 Godot 猜，行为不可控。
  写 SVG 资源时按「正常图标」的写法对齐，别从别处拷一个裸 path 就用。
- **排查图标显示异常时，先打印贴图的 get_width() / get_height()**：
  比预期大很多（比如 512）就是缺尺寸信息，比预期小就是 path 坐标画布不匹配。
- 改完 SVG 源文件后 Godot 会**自动重新导入**（.import 里的 md5 变了），
  不用手动清 .godot/imported 缓存。

## 39. 同一张图里两个元素用了两套坐标系 —— 先量清楚谁是基准

主人先报「实心六边形和青色描边不重合」，修完一轮又报「代表我的图标，和我实际所在的格子不一致」。

### 先量，别猜

这类"看着错位"必须先把**每个元素的几何中心**算出来打日志对比，
而不是凭直觉去改那个"看起来更可疑"的。

修复前（我误改之后的状态）：

`
格子节点 Position=(375,351) Size=(180,156)   ← Position 是【左上角】不是中心
HexShape 顶点中心    =(0,0)  → 画在 (375,351) = 格子左上角 ❌
HighlightLine 点中心 =(0,0)  → 画在 (375,351) = 格子左上角 ❌
玩家图标 中心在格子中心                   → 与上面两者差 (90,78) ❌
`

修复后（三方中心完全重合）：

`
格子节点 @Control@12   global rect = (870,480) 180×156   ← Position 是【左上角】
HexShape（填色）      顶点 x∈[15,165] y∈[0,156] → 中心 (90,78) → 全局 (960,558)
HighlightLine（描边）  点 (15,39)(90,0)…(15,117) → 中心 (90,78) → 全局 (960,558)
玩家图标              rect (935,533) 50×50     → 中心 (960,558)
`

### 真正的根因

`HexMapUI.HexToWorld(coord)` 返回的是格子的**左上角**（`x = 150*Q + 75*R, y = 117*R`），
`CreateTileView` 直接 `tileView.Position = worldPos` → **格子节点的原点在左上角**。
玩家图标也按「左上角 + 半个格子 − 半个图标」定位 → 同样以左上角为基准。

而规则文件 `.trae/rules/project_rules.md` 里的六边形顶点
（V0(90,0) V1(165,39) V2(165,117) V3(90,156) V4(15,117) V5(15,39)）
本来就是**相对格子左上角**写的 → **填色 `HexShape` 一直是对的**。

真正错位的是 **`HighlightLine`**：`.tscn` 里硬编码了中心原点坐标
（`(-75,-39) … (0,-78) … (75,39)`）→ 描边整体偏了 (−90,−78)，画到了格子的左上角。
这就是主人最初看到的"填色和描边不重合"。

### 我把它修反了

我当时的判断是"填色用了左上角原点 → 填色偏了"，于是把 `UpdateHexShape` 改成中心原点。
结果**把本来正确的填色改错了**：填色和描边一起跑到格子左上角，
而玩家图标还在格子中心 → 主人的第二张图「图标和所在格子不一致」。

**正确修法**：两者统一用左上角原点坐标。`HexShape` 顶点恢复规则文件那套，
`HighlightLine` 的 `points` 也改成同一套。

### 教训

- **改之前先量谁是基准**。本例里正确的是填色、错的是描边；我挑错了下手对象，
  把一个对的改成错的，还制造了一个更明显的新 bug。
- **规则文件给的坐标是相对什么原点，必须先确认当前节点的原点在哪**。
  本项目的格子节点原点在**左上角**（因为 `HexToWorld` 返回左上角），
  跟"节点通常在中心"的直觉相反。
- **同一视觉元素的多层（填充/描边/图标）必须共用同一坐标系**。
- **「看着错位但点击正常」= 纯视觉问题**，别去查点击命中逻辑
  （本项目这里命中走矩形 `Rect2`，正好绕过了多边形）。
- 排查手段一：把各元素的**几何中心**（顶点均值）打出来三方对比，偏差一目了然。
- 排查手段二：把可疑元素**涂成鲜红色**再截图 —— 形状和位置在图上一眼可辨，
  比盯着灰白色块猜靠谱得多（本次就是这样确认六边形与图标严丝合缝的）。

## 40. TextureRect 缺 expand_mode → 节点被撑到贴图原生大小

主人发现地图右上角有两个**巨大的蓝色史莱姆**（其实是 enemy_cultist.svg 的完整形象：
深蓝圆角方块 + 青色发光的笑脸），而它本该是格子中央的一个 80×80 小图标。

数据：

`
IconRect 节点尺寸 = 512×512     ← 应该是 80×80
贴图原生     = 512×512
expand_mode  = 0 (IGNORE_SIZE)  ← 问题在这
`

**根因**：TextureRect 有两个容易混的属性：

| 属性 | 作用 |
| :--- | :--- |
| expand_mode | **节点尺寸由谁决定** |
| stretch_mode | 贴图在节点内**怎么画** |

expand_mode 默认是   = IGNORE_SIZE → **节点尺寸 = 贴图原生大小**，
stretch_mode 只管贴图在这个节点里怎么缩放。
所以哪怕 .tscn 里 anchor/offset 写的是 ±40（= 80×80），节点照样被撑到 512×512。

**实测各值的效果**（custom_minimum_size = 80×80 + stretch_mode 随便）：

`
expand_mode=0 (IGNORE_SIZE)  → 节点 512×512   ← 撑开
expand_mode=1 (KEEP_SIZE)    → 节点 80×80     ← 正确
`

> 注意方向和直觉相反：**expand_mode=1（KEEP_SIZE）才是「保持我给的尺寸」**。
> 名字里的 "expand" 指的是「允许节点被撑大」，不是「保持大小」。

**修法**：给所有 TextureRect 补 expand_mode = 1（custom_minimum_size 只是下限，拦不住）。

**本项目补了 16 处**：HexTileView（格子图标）、AttackerDisplayUI（头像 + 怒气圈 ×8）、
Card（类型图标）、KeyOrderSelectionUI（钥令图标 ×3）、两个刻印选择界面（刻印图标 ×2）。

**教训**

- **TextureRect 写进 .tscn 时，expand_mode 和 stretch_mode 要成对检查**。
  只写 stretch_mode 是这个项目里最容易漏的坑（漏了就是「图标巨大化」）。
- **custom_minimum_size 挡不住撑开** —— 它只是最小值，expand_mode=0 时节点照样涨到贴图大小。
- **排查手法**：跑起来 dump 每个 TextureRect 的 size 与 	exture.get_width()/get_height()，
  「节点 > 贴图原生」就是撑开了。也可以一行扫出所有缺 expand_mode 的节点。
- 这个坑和 §38（SVG 缺 viewBox）是**同一类问题**：都是「资源尺寸信息不全 → 渲染尺寸失控」，
  但修法不同（一个补 SVG 属性，一个补节点属性）。

## 41. 位置变化有多条路径，只改一条就会漏

主人报：从传送门传送到目标点时，**迷雾没有解除**，落点周围一片黑，
看不见自己站在哪、也看不见相邻能走哪。

两条路径的代码对照：

`
走路   HexMapController.MoveTo → OnPlayerMoved      → _controller.RevealTiles(newPos, 1) + UpdateFogAndHighlight()  ✅
传送   HexMapController.TeleportPlayer → OnPlayerTeleported → 只挪图标，没照亮、没刷新迷雾              ❌
`

`TeleportPlayer` 里 `OnPlayerTeleported?.Invoke(_currentPosition)` 触发的回调，
**只做了「挪图标 + 设当前格 + 清路径高亮」**，漏了走路路径里的两行：
`_controller?.RevealTiles(newPos, 1)` 和 `UpdateFogAndHighlight()`。

**修法**：把这两行补进 `HexMapUI.OnPlayerTeleported`，与 `OnPlayerMoved` 完全一致。

**教训**

- **凡是「玩家位置变了」这件事，所有后继副作用都要逐条对齐**。
  本项目位置变化有 3 条路径：`MoveTo`（走路）、`TeleportPlayer`（传送门）、
  `TeleportPlayerTo`（调试/直接指定）。后两条里 `TeleportPlayerTo` 走的是
  `OnPlayerMoved`，所以只有传送门那条漏了。
- **「走路正常」不代表「传送正常」** —— 两条路径共用一个"效果函数"时，
  最容易只改其中一条调用点。
- **修完要跑真实链路，别只测被改的那行**。本次用临时 C# 集成测试断言 4 件事：
  落点被照亮 / 落点周围一圈被照亮 / 落点格子视图 `IsFogged == false` /
  远处格子仍是迷雾（没过度照亮），8/8 通过。
- 顺带一提：**测试断言本身也会写错**。第一次我把"照亮总数增量"写成
  `落点 + 全部邻居`，但没算上邻居里**早就照亮**的格子 → 误报 FAIL。
  `RevealTiles` 只计**新增**照亮的格子，断言必须按"新亮了多少"算。
- **autoload 里的临时测试比场景先就绪** → 拿不到 `HexMapController.Instance`
  和 `HexMapUI`。要用 `await ToSignal(GetTree(), SceneTree.SignalName.ProcessFrame)`
  轮询等场景加载完，否则测试会误判成"找不到节点"。
- **headless 跑不起来主场景**（只加载了 autoload）→ 要验 UI 必须用
  godot-runtime MCP 的 `run_project(scene="Scenes/Dev/DevScenario.tscn")`。
