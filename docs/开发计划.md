## 1. 三步工作流

每个条目都必须走完这三步才算完成，跳步即视为未完成。

### 第 1 步 · 需求

**输入**：主人的指示 + 参考图编号。

**我要产出**（缺一项就动手 = 耍赖）：

1. **做什么** —— 一句话说明改哪个界面 / 哪个文件
2. **长什么样** —— 元素清单、参考图编号、要填的数值
3. **验收点** —— 什么现象算做完了，能被截图或日志证明

**准入**：条目三要素齐了才进开发。
**准出**：主人认可需求表述。对参考图的解读有歧义时，先复述一遍再动手。

> 🔺 **难度最高**（D12 地图多簇生成）与 🔺 **重要度核心**（D13 地图校验器）额外要求：动手前先出一版**分阶段方案**给主人过目，确认「回退路径」成立后再写第一行代码。

### 第 2 步 · 开发

**顺序**（铁律见 `.trae/rules/project_rules.md`）：

0. **动代码前先查 [`docs/踩坑记录.md`](踩坑记录.md)** 有没有同类坑。本项目 UI 的三个高频坑：
   §8 根节点漏绑 script、§10 子节点也要挂脚本且一个 .cs 只能一个类、§11 事件驱动的初值要手动推一次。
1. 布局写进 `.tscn`（UI 优先建独立场景，禁止代码硬编码坐标）
2. 逻辑写进 `.cs`（一个 `.cs` 只挂一个类，根节点和槽位节点都要挂）
3. 事件回调**首行** `GD.Print($"[类名] 方法名 called")`、**末行** `... completed`
4. 挂进父场景 / 接到现有管理器上

**准出**：`dotnet build` 0 错。新增 `.tscn` 引用的资源必须真实存在。

### 第 3 步 · 验证

**我做**（后台跑，不抢主人鼠标）：

- 用 `Scenes/Dev/DevScenario.tscn` + 预设进场景，`background: true`
- **主动把关键截图和日志原文贴进聊天**，不只汇报「通过了」
- **改完文档要回读**：把文档里写的数字 / 链接 / 表格与**代码和数据**对一遍
  （已固化进 `tools/check-doc-consistency.ps1`：规模数字 / 条目数 / 踩坑条数 / 目录表覆盖）
- 断言按条目里的「验证」栏执行

**主人做**（通过后）：

- 我开**可见模式**的调试场景准备器窗口，主人自己点、自己验证、**自己关**，我不 stop
- 主人反馈后我改，改完重跑第 3 步

**准出**：截图证据 + 主人确认。**没贴截图就不算验证过。**

**四种验证形态**（每个条目的「验证」栏必须指明用哪几种）：

| 形态 | 含义 |
| :--- | :--- |
| 视觉 | 截图与参考图对照，看布局/配色/层级对不对 |
| 行为 | 点哪里 → 发生什么，是否符合预期 |
| 数据 | 日志里的具体数值（如 `携带地图血量进入战斗: 125/125`） |
| 回归 | 相关旧流程没被改坏（如打完 BOSS 还能回图） |

**重要度**：🔺 核心（是别的条目的前提 / 通用资产）｜ 高（玩家能直接感知，或多界面共用）｜ 中 ｜ 低。
**难度**：🔺 最高（核心算法，多数 AI 写不对）｜ 高 ｜ 中 ｜ 低。

**排序理由**

1. **D13 第一** —— 主人指出关卡可以人工配置，但真正必需的是**校验**：有没有走过去了回不来、有没有通不了关。这套算法是**有向图可达性 + 死锁检测**，换个邻接函数就能用在别的项目上，是**能带走的资产**。它还是后续一切地图改动（D5 显示三态、D12 多簇、D14 配额生成、人工关卡）的**安全网**。
2. **D14 第二** —— 关卡是**固定内容**（重复进入要一样），但不必逐格手画：用**配额参数**（多少格、几个战斗/精英/商店/单向门/双向门）生成即可。关键是**确定性 + 结果复用**，否则每次进关卡地图都变。
3. **D12 第三** —— 主人两度澄清：簇有**两个来源**——**初始就多簇**（靠传送门连；传送门是**永久超边**）+ **洞消耗后再分裂**（洞是**一次性节点**，消耗后该簇裂成两块）。所以生成器**两件事都要做**：造 N 个互不连通的簇并用传送门连起来（≥ N-1 对）+ 在簇内割点埋 1~3 个洞。**难度 🔺 最高 → 高**（簇形状用随机游走生长即可，簇间靠**传送门**而不是靠"留空隙"来隔开），**重要度高**（它是参考图 R-05/R-06 那种观感的来源）。
4. **D1 第四** —— 地图/战斗/商店三类界面共用的顶部 HUD，做一次到处受益，是所有界面改造的前提。
5. **D4 / D7 第五六** —— 玩家流程上的两个断点：打完没有结算界面、事件弹窗两套样式（D5 的探照灯事件也复用这个面板）。
6. **D5 第七（重要度/难度都升到高）** —— 迷雾系统是探索感的核心，R-15 / R-16 / R-17 三张图把机制说全了：**战争迷雾** + 相邻格高亮 + **探照灯道具** + 已照亮状态持久化。难度高在两处：程序化云雾边缘、动地图存档。
7. **D3~D11 中段** —— 战斗信息补全、视觉主题、选关卡升级。难度与重要度都中等，顺序可调。

### D15 · 刻印触发（跨战斗存活 + 出牌生效） ✅

**需求**：刻印效果在出牌时真正触发；刻印状态跨战斗存活；卡面能看出刻了印。

**根因**：EngravingManager.OnCardPlayed **全项目零调用点**；且战斗卡组每场由 Attacker 重新 new 出来 —— 即使刻了印，下一场战斗那张卡也是全新的（IsEngraved=false）。

**实现**：
- EngravingManager 升为 **autoload**（刻印必须跨场景存活，对齐 MapManager / BlackMarkShopManager 的既有做法），内部持有 cardId → EngravingEffect 映射。
- 新增 ApplyToDeck(deck)：战斗建卡组后把刻印**回填**到对应卡上（否则刻印每场必丢）。
- BattleManager.OnCardPlayed 调 TriggerEngraving(card) → 触发 6 种刻印效果（护盾/中毒/复制/团队怒气/自身怒气/易伤），并把描述打进战斗日志。
- 卡面右上角加 EngravingIcon 角标（Card.tscn 布局 + CardUI.cs 逻辑），图标资源做存在性检查。

**验证**：临时 C# 集成测试 15 条断言（写入 / 查询 / 回填 / 触发 / 未刻印不触发 / 跨场景存活 / ClearAll）。

### D16 · 怒气大招真正生效 ✅

**需求**：大招要有实际效果；怒气满时能点角色释放；释放后怒气清零。

**根因**：UltimateSkill.Execute 只遍历 GetEffects()，而所有大招的 EffectIds **都是空的** → **大招实际效果为零**。且数据源读的是 characters.json 内嵌的旧版（字段更少），更完整的 ultimates.json 根本没被用上。

**实现**：
- UltimateLoader 补齐被丢弃的字段解析（isAreaAttack / 	arget / pplyDebuffName / energyGain / description）。
- UltimateSkill.GetUltimateById 优先级改为 **ultimates.json → characters.json → 硬编码兜底**。
- 新增 UltimateExecutor：目标解析（area/front/rear/random）→ 伤害 → 减益 → 治疗 / 护盾 / 抽牌 / 能量，每步打日志。
- CharacterPosition.TryUseUltimate(...) 返回是否成功 + 中文摘要；怒气不足拒绝且**不消耗**怒气；成功则**怒气清零**。
- UI：CharacterSlotUI 加点击回调 + 「可释放」徽标（UltReadyLabel），AttackerDisplayUI 转发槽位索引 → BattleManager.OnUltimateSlotClicked。

**验证**：临时 C# 集成测试 9 条断言（数据源字段 / 怒气不足拒绝 / 怒气清零 / 造成伤害 / 中文摘要）。

### D17 · 钥令效果与每回合 2 次限额 ✅

**需求**：钥令效果真实生效；每回合最多用 2 次。

### D20 · 地图空洞（中间「没有格子」的区域） ✅

**需求**：主人指出当前地图是一整块密实的格子，**整个地图所有格子都能到达**，
看着不像"地图"。要求：**中间留些走不进去的地方 —— 那个地方根本没有格子**，
并且**逻辑要自洽：别把事件生成到不能到达的格子**。

**和「洞」的区别（两回事，代码与文档都要分清）**：

| | 洞（`HexEventType.Hole`） | 空洞（`MapQuota.Void`） |
| :--- | :--- | :--- |
| 有没有格子 | **有**，踩上去才塌陷消失 | **一开始就没有** |
| 作用 | 一次性节点，消耗后该簇裂成两块 | 地图的空白区，永久走不进去 |
| 配额字段 | `quota.hole` | `quota.void` |

**实现**：
- `MapQuota` 增 `Void` 字段（空洞**片数**）+ `VoidTileCount`（最多挖掉多少格）；`MapSpec` 解析 `"void"` 并做 0~4 的可满足性校验。
- `Data/level_specs.json`：map_01/02 各 2 片、map_03 3 片。
- `HexMapGenerator.CarveVoidRegions(...)`：
  1. 只挖**内部**格子（6 个邻居都在图里，或已经是空洞）→ 空洞是"中间的一个洞"，不是边缘缺口；
  2. 只挖**不是割点**的格子（连通块数变化判断）→ 挖完地图仍然连通，起点→终点仍然连着；
  3. 整片挖完复检（起终点还在 + 连通块数没变），不满足就**回滚重试**。
  4. 挖洞用**独立的随机流**，不打乱后续（传送门 / 事件）的布局 —— 只在原图上"挖掉几格"，其余保持原样。
- **顺序**：挖洞排在**所有事件铺放之前**（传送门 / 洞 / 探照灯 / 沼泽 / 战斗…），
  所以事件**不可能**落在被挖掉的格子上。
- **自洽校验**（新增 `VerifyAllEventTilesReachable`）：事件铺完后，**每一个事件格都必须能从起点到达**
  （传送门算超边）→ 不满足就重生成地图。
- `HexMap` 记录 `VoidCells`（被挖掉的坐标），供断言与后续渲染使用。

**顺带修掉三个被空洞改动暴露的既有 bug**：
- **探照灯会盖掉洞 / 盖掉传送门** —— `PlaceSearchlightTiles` 的候选没过滤 `EventType` →
  洞的配额悄悄少一个、传送门配对会断。改为只落在空格上。
- **洞被撤销后不补放** —— 挖洞会改变割点集合，原本是割点的落位可能失效 →
  复检后按缺口补放。
- **沼泽落位不足** —— `PlaceSwampTiles` 遇到"不能挨着沼泽"的格子就跳过、不重试，白吃配额 → 改为遍历全部候选。

**验证**：临时 C# 集成测试 24/24 通过（3 张规格 × 8 条断言）：
挖出了空洞 / 空洞格确实不在地图里 / 空洞被地图包围（不是边缘缺口） /
终点可达 / **所有事件格都可达** / 没有孤岛 / 确定性（同规格两次生成逐格一致） /
挖洞与不挖洞对比（洞数、事件数完全一致，只少了格子）。
另附截图确认：地图上能看到缺口。

### D21 · 可达性实现统一（消除三套口径） ✅

**需求**：D20 验收时发现 —— `HexMap` 的公开可达性 API（`IsReachable` / `VerifyMapReachable` /
`FindShortestPath` / `GetCriticalPathTiles`）**不认传送门**，在跨簇地图（map_02 / map_03）上
把明明能通关的地图误判成「不可达」。

**根因：同一个语义有三套实现，口径分叉了**：

| 实现 | 传送门算不算边 | 位置 |
| :--- | :-- | :--- |
| D13 校验器 | ✅ 算 | `MapValidation/HexMapGraph.cs` |
| 生成器内部 | ✅ 算 | `HexMapGenerator.BuildTeleportIndex`（私有副本） |
| 控制器内部 | ✅ 算 | `HexMapController.VerifyReachable`（私有副本） |
| **`HexMap` 公开 API** | ❌ **不算** | `HexMap.IsReachable` / `FindShortestPath` / `GetCriticalPathTiles` |

**但不能一刀切全改**：传送门有两种**语义相反**的处理口径，混在一起才是病根。

| 用途 | 传送门 | 为什么 |
| :--- | :-- | :--- |
| **地图可达性判定**（能不能通关） | **必须认** | 传送门是地图的一部分，是跨簇唯一的通道 |
| **自动寻路**（玩家点远处格子自动走） | **必须不认** | 穿门要弹窗确认，不能自动走过去 |

**实现**：
- `HexMap` 成为**唯一实现处**：`ComputeTeleportIndex` / `ComputeReachableTiles` / `ComputeShortestPath`
  三个静态方法（`includeTeleports` 显式传参，不给默认值 —— 避免以后误用）。
- 实例方法全部转调：`IsReachable` / `VerifyMapReachable` / `GetCriticalPathTiles` 一律**认**传送门；
  `FindShortestPath(start, end, includeTeleports)` 由调用方显式声明口径。
- **删掉两份私有副本**：`HexMapGenerator.BuildTeleportIndex` / `FindShortestPath` / `ReconstructPath` /
  `GetReachableTilesWithTeleports` / `VerifyReachable` 全部删除，生成器改调 `HexMap.ComputeShortestPath`。
- `HexMapController.MoveTo` / `GetPathTo` 显式传 `includeTeleports: false`（自动寻路不穿传送门），
  并在代码旁写明原因。
- D13 校验器（`MapValidation/HexMapGraph`）**保持独立** —— 它建的是带边种类的图，给状态空间搜索用，
  而且这一套本来就设计成可整目录拷走复用。

**净效果**：代码净减 85 行（3 个 `.cs` 合计 +155 / −240），可达性实现从 3 份收敛到 1 份。

**验证**：临时 C# 集成测试 24/24 通过（3 张规格 × 8 条断言，测完即删）：
**回归**（地图内容与重构前逐项一致：格数 / 起终点 / 空洞数）/
`IsReachable` 为 true / `VerifyMapReachable` 为 true / `FindShortestPath(认传送门)` 非空 /
`GetCriticalPathTiles` 非空 / **自动寻路的路径里没有「跳传送」那一步** /
跨簇地图「相邻走不通、认传送门走通」/ 相邻格寻路仍有效。

### D22 · 全称可达性保证（无论怎么走都能到终点） ✅

**需求**：主人把要求说清楚了 —— **「从起点出发、战斗都赢的情况下，无论怎么走都能到终点见到 BOSS」**。
这比原来的保证强一档：原 D13 给的是**存在性**（「存在一条走法能通关」），
主人要的是**全称**（「任何走法都不会把玩家困死」）。

**问题出在洞（消耗型格）上**。洞是**消耗型**格子：踩上去还能站，离开时**该格被删除**。
旧规则把洞放在「簇的窄口」（旁支入口）：

```
玩家走进旁支 → 踩洞 → 洞被消耗 → 旁支入口消失 → 玩家被困在旁支里 → 永远到不了 BOSS
```

静态层查不出（洞还在时旁支仍能经洞回到终点 → 不算软锁），
只有**状态空间**（把「哪些洞已被消耗」也当状态）才看得见；
而旧的状态空间搜索**一找到通关走法就 return** → 只验存在性，验不出「别的走法会死」。

**改之前的实测**：`map_01/02/03` 的 `CanCompleteGoal` 全是 True，但**死局状态分别有 10 / 12 / 12 个**。

**实现**：

1. **校验器加全称判定**（`MapValidator.SearchDeadEndStates`）
   - 正向枚举所有可达状态（位置 / 已消耗洞集合 / 进洞来源格），并记录状态之间的边
   - 建**反向边**，从「站在终点」的状态反向 BFS → 得到「还能到终点的状态」集合
   - 可达状态里不在那个集合里的，就是**死局状态**
   - 状态转移规则抽成 `TryStep()` **一份实现**，存在性搜索与全称搜索共用（别抄第二份）
2. **报告与门控**
   - `MapValidationReport` 新增 `CanAlwaysReachGoal`（全称判定）与 `DeadEndStateCount`
   - `MapIssueType` 新增 `DeadEndState`
   - 生成器把关升级：`!CanAlwaysReachGoal` → **重新生成地图**（原来只有 `!CanCompleteGoal` 才拦）
3. **生成器的洞落位改成「试放 + 裁决」**
   - 逐个候选格试放一个洞，跑一次全称判定；通过就留下，不通过就撤掉换下一个
   - **判据只有校验器那一份实现**，生成器不自己再抄一遍（抄了必然口径分叉，见 §43）
   - 割点优先（消耗掉割点地图才会分裂 = D12 的核心观感），但最终由全称判定裁决
4. **删掉旧的「洞必须是割点 → 不是就撤销 → 再补放」** —— 新落位已自带裁决，
   而且旧判据（纯邻接算割点）在跨簇地图上本来就是错的

**改之后的实测**：

| 地图 | 全称判定 | 死局状态 | 洞数/配额 | 重试 | 问题数 |
| :--- | :-- | :-- | :-- | :-- | :-- |
| map_01 | True | **0** | 2 / 2 | 0 次 | 0 |
| map_02 | True | **0** | 3 / 3 | **1 次** | 0 |
| map_03 | True | **0** | 3 / 3 | 0 次 | 0 |

> map_02 那 **1 次重试**是新门控真的在拦人：第一次生成的图有死局 → 被拦下 → 换了一张。
> 这是「门控有效」的证据，不是 bug。

**验证**：临时 C# 集成测试 18/18 通过（3 张规格 × 6 条断言，测完即删）：
全称判定为 True / 零死局状态 / **存在性老口径没被破坏** / 洞数与配额一致 /
所有事件格都可达 / 同规格两次生成逐格一致。
另：`tools/verify-mapvalidation-portability.ps1` 仍 6/6 通过（模块可整目录拷走）。

**已知取舍**：洞现在**不保证是割点** —— 地图太「胖」时，安全的割点一个都没有
（能当割点的全是「消耗掉会把玩家困死」的旁支窄口）。此时洞退化成「消耗型的一次性格子」，
「消耗后分裂」的观感会弱一些，但**保证优先**。

### D13 · 地图可达性与死锁校验（通用算法模块） 🔺 **最高优先 · 可移植** **已完成** ✅
**为什么它排第一**

- 主人指出：关卡可以是**人工配置**的，那么真正必需的不是"随机生成"，而是**"校验"**——有没有走过去了回不来、有没有通不了关。
- 这套东西本质是**有向图可达性 + 死锁检测**。换个邻接函数就能用在方形网格、卡牌爬塔的房间图、任何"格子 + 传送"结构上 → **能直接带到别的项目**。
- 它是**后续一切地图改动的安全网**：D5（显示三态）、D12（多簇）、**D14 配额生成**、将来的人工关卡编辑，全靠它兜底。先有网，再动刀。
- 换个身份看它：**它是「这张地图合不合法」的唯一判定标准**。人工配的关卡、参数生成的关卡，都用同一套标准判。

**需求**

一个**独立、可移植**的校验模块：输入「节点 + 有向边 + 关键节点集」，输出**结构化诊断报告**（不是 bool）。至少能检出这 6 类问题：

| # | 问题 | 玩家感受 | 判定方式 |
|---|---|---|---|
| 1 | **通不了关** | 玩到一半发现走不到 BOSS | 起点 → 终点在有向图上不可达 |
| 2 | **走过去了回不来（软锁）** | 踩进某个格子后再也出不去 | 存在格子 x：x 从起点可达，但 x → 终点**不可达** |
| 3 | **不可达区域** | 地图上有一大片永远去不了 | 存在不在「起点可达集」里的格子 |
| 4 | **关键格不可达** | 必经事件/商店/BOSS 被隔断 | required 节点 ∉ 可达集 |
| 5 | **死路** | 进去才发现是死胡同 | 出度为 1，且唯一出边是**单向**传送 |
| 6 | **孤岛 / 多簇** | 有一块区域跟主线完全断开 | 全图弱连通分量数 > 1 |
| 7 | **消耗型格子导致的状态死锁** | 走过一次「草盖地洞」后原路没了，后面过不去 | **需要状态空间分析**，静态图判不出来 |

报告必须**逐条列出问题格子**（坐标 + 类型 + 原因），不能只说"有问题"。

**建模：传送是有向边** ← 这是整个算法成立的关键

| 移动方式 | 图上的边 |
|---|---|
| 邻接移动（六边形相邻格） | 双向边 |
| **单向传送** | **1 条有向边**（走过去就回不来） |
| 双向传送 | 2 条有向边 |

于是"走过去了回不来"**自动变成有向图上的可达性问题**，不需要任何特判——这是把传送当有向边建模换来的干净。

**但有向边还不够：还有「消耗型格子」（草盖地洞）**

参考游戏里有一种格子：盖着草的地洞。规则已确认（主人 2026-10-20）：

```
玩家在 A  →  踩进 D      D 还在，但**不允许退回 A**
            →  从 D 走到 B  **D 被删除**（变空格，不可走）
            →  在 B         永远回不到 A 侧
```

- 每关 **1~3 个**，**消耗必定、一次性**
- 这不是静态图能表达的 —— **图本身在变**
- 正确建模是把**不可逆元件的状态并进搜索状态**：

```
状态 = (当前位置, 已消耗的洞集合, 进入当前洞的方向)
```

- **k=0 时自动退化成普通 BFS**；k ≤ 3 时状态数 = N × 2³ × 常数，**完全可枚举**
- **复杂度取决于 k（不可逆元件的数量），不是地图大小 N** —— 这是这条路能走通的关键

好消息：本作是**单 agent、无谜题分支**的（玩家按顺序走，不像推箱子要解谜），
所以只需回答「**是否存在一条能通关的走法**」这个**存在性问题**，在状态图上跑一次 BFS 即可，**不需要搜索完整解法**。

| k（每关消耗型格子数） | 状态数（N=50） | 可行性 |
|---|---|---|
| **1~3（实际取值）** | 400 ~ 3,200 | **完全可枚举，微秒级** |
| 5 | 1,600 | 毫无压力 |
| 10 | 51,200 | 仍然轻松 |
| 20 | 5,120万 | 边界，需要剪枝 |

**🟢 两层判定：簇图预检 + 状态空间兜底**

**洞 = 可消耗的通道节点**（它是个**顶点**，消耗后这个格子从地图上消失）。

**第 1 层 · 簇图预检（O(V+E) 静态，快速筛）**
1. 移除所有**洞节点**
2. **缩簇**：只把「邻接边 + **双向**传送超边」算作连接 → 得到若干**簇**
   （**单向门不算**连接边——它是有向的；**洞**也不算——它是消耗型的）
3. 得到**簇图**：节点 = 簇，边 = 单向门 / 双向传送门 / 洞
4. 在簇图上做**有向 BFS**（正向 from S、反向 from BOSS）→ 「能到的簇」与「能到 BOSS 的簇」
5. **判定：所有 required（含 BOSS）是否都落在「能到 ∩ 能到 BOSS」的簇里**

**第 2 层 · 状态空间搜索（主判定）**
状态 = (位置, 已消耗洞集合, 进入当前洞的方向)，在状态图上 BFS。
k ≤ 3 → 状态数 ≈ N × 2³ × 常数 ≈ 3,200，**微秒级，直接枚举，无需剪枝**。

**为什么必须这样**：簇**内部**是普通双向边 → 自由往返，簇内所有格子都访问得到；
簇**之间**只能靠单向门 / 双向传送门 / 洞，而**洞消耗后不能回**。
玩家在簇图上走：永久边可反复走，**一次性边只能走一次** → 拐进不该去的方向就再也回不来。

三个例子（用簇的视角画）：

```
❌ 死锁：required 落在只能单向进入的旁支簇
        [R_A] ← required 在这
           │(单向门，只进不出)
          [S]────[E]

✅ 合法：required 都在路径簇上
   [S]──(双向传送)──[E]

❌ 死锁：required 落在旁支簇（洞消耗后裂出来的）
        [R_A] ← required
           │(洞，用掉即断)
          [S]──(洞，用掉即断)──[E]
```

附带一条隐含约束：**S 侧簇里的 required 必须在离开该簇之前访问完**（簇内自由可达，所以自动满足）。

> ⚠️ **术语纠正**：洞是**顶点**（格子），消耗后消失，所以要判断的是它是不是**割点**
> （articulation point，删掉它会断开两个区域），**不是「桥」（cut edge，指的是边）**。
> 若洞**不是割点**（在环上、两侧另有通路），玩家穿过后仍能绕路回来，只是那个格子没了 ——
> 这种洞**不会**造成簇分裂，簇图预检自然不报，交给状态空间确认。

> 📌 **关于奇偶性**：决定性的是「**S 到 E 的路径上穿过了几个洞（m）**」，**不是**「地图上一共有几个洞（k）」——地图上有 5 个洞但路径上只用 1 个，跟地图上就 1 个洞，是同一回事。
> 若 m = 0 → S 与 E 同一簇；m 为奇数 → 玩家最终停在 E 侧（不同簇）；m 为偶数 → 玩家回到与起点同侧。
> **真正决定成败的不是奇偶本身，是旁支簇里有没有 required 格子** —— 奇偶只是这个判断的副产品。

**这一条把难度降下来了**：第 1 层是 **O(V+E) 静态算法**（大规模快速筛），第 2 层状态空间在 **k ≤ 3 时完全可枚举**（微秒级），两层都不需要复杂剪枝。

**算法**

1. 建图：节点 = 格子，有向边 = 邻接 + 传送；**洞（消耗型格子）单独标记**
2. **正向 BFS**（从起点）→ 可达集 **R**（静态层，k=0 时的答案）
3. **反向 BFS**（从终点）→ "还能到终点"的集合 **T**
   - ⟹ 格子 x ∈ **R \ T** ⟹ **走进 x 就通关无望**（软锁区）——这就是第 2 类问题
4. 关键格校验：required ⊆ R，且到它的路径上不强制经过单向传送
5. 死路：出度 = 1 且唯一出边是单向传送
6. 孤岛：全图弱连通分量数
7. **状态空间搜索（主判定，有洞时必做）**
   - 状态 = **(位置, 已消耗洞集合, 进入当前洞的方向)**
   - 转移规则：

     | 当前 | 动作 | 结果 |
     |---|---|---|
     | 普通格 x | 走到邻格 y（y 是未消耗的洞） | 进入洞，**记下进入方向**，**禁止退回 x** |
     | 洞 D 内 | 走到 D 的**其他**邻格 | **D 被消耗（删除）**，已消耗集合 ∪ {D} |
     | 洞 D 内 | 退回进入方向 | **禁止**（这一步走不了） |
     | 任意 | 走到**已消耗**的洞 | 不可走（格子已删除） |

   - 终止判定：存在状态满足「已访问全部 required（含 BOSS）」且「当前位置 = BOSS」
   - **k ≤ 3 → 状态数 = N × 2^k × 常数 ≈ 3,200，直接枚举，无需任何剪枝**
8. **簇图分析（★ 核心机制，不只是预检）**
   - **簇的划分**：移除所有**洞节点** → 缩区域 → 得**簇**。缩区域时：
     - ✅ **必须算**「邻接边 + **双向**传送超边」
     - ❌ **单向门不算连接边**（它是有向的，只提供单向通行）→ **单向门两侧是不同的簇**
     - ❌ 洞也不算（消耗型的，用掉即断）
   - **簇图上的边有三种**：

     | 边 | 方向性 | 可否重复用 | 用掉后 |
     |---|---|---|---|
     | 双向传送门 | 双向 | 可 | 仍在 |
     | **单向门** | **单向** | 可 | 仍在（但只能一个方向） |
     | 洞 | 单向 | **不可** | **断开** |

   - 玩家在簇图上走：永久边可反复走，一次性边只能走一次
   - **簇层的有向 BFS**（从 S 正向、从 BOSS 反向）→ 得「能到的簇」与「能到 BOSS 的簇」
     - 两者之差 = **软锁簇**（进得去出不来）
     - 这给出**乐观上界**（假设洞都还在），用来**快速筛掉肯定不通的情况**
   - **为什么它是核心**：簇有两个来源——**初始多簇** + **洞消耗后再分裂**；
     簇图**就是这个机制的原生模型**，不是辅助分析
   - ⚠️ **洞不是割点就不起分裂作用**：只有当洞是**割点**（删掉它会断开两个区域）时，消耗后才会造成簇分裂；
     若洞在环上（两侧另有通路），穿过后仍能绕路回来，只是那个格子没了 ——
     这种洞**不会**影响区域划分，簇图判定自然不报，交给状态空间确认
9. 输出报告：问题类型 + 坐标 + 建议

**开发**

### D14 · 按配额生成关卡地图（确定性 + 可复用） 🔺 **高优先** **已完成** ✅
**为什么既不是"人工配置"也不是"每次随机"**

主人的观察：关卡**重复进入的时候是一样的** → 关卡是**固定内容**。但逐格手画不现实；每次进关卡重新随机也不对。所以正确形态是 **参数化生成 + 确定性 + 结果复用**：

- **规格（配额）**：关卡只声明「多少个格子、几个战斗格、几个精英格、几个商店格、几个单向门、几个双向门……」，不声明具体布局
- **确定性**：同一份规格 + 同一个 seed → **同一张地图**（可重建、可复现、可分享）
- **可复用**：关卡第一次进入时生成并缓存，之后每次进入拿同一张

**现状与设计意图不符（读代码确认，不是猜测）**

| 事实 | 位置 | 后果 |
|---|---|---|
| `new HexMapGenerator()` **没传 seed** | `HexMapController._Ready()` line 80 | 内部 `new Random()`（系统时钟种子）→ 每次首进关卡都是**全新随机图** |
| 战斗返回地图走 `RestoreMapState()` | `HexMapController` line 91-98 | 从 `BattleTransitionManager`（autoload，**仅内存**）恢复 → 同一局内进出是同一张 ✓ |
| 但**退出游戏重进同一关卡** | — | 又是一张新图 ✗ 与「关卡固定」的设计意图不符 |

**需求**

1. **规格数据**：新增 `Data/level_specs.json`，每关一份配额
   ```json
   {
     "mapId": "map01",
     "seed": 20261020,
     "clusters": 3,
     "totalTiles": 42,
     "quota": {
       "battle": 6, "elite": 2, "shop": 1, "heal": 1,
       "blackMark": 2, "swamp": 1, "hole": 2,
       "teleportOneWay": 1, "teleportTwoWay": 3,
       "oneWayConsumable": 2
     }
   }
   ```
   > `clusters` = 初始簇数（簇**之间靠传送门连通**，传送门对数 ≥ `clusters` - 1）
   >
   > `teleportOneWay` = **单向门**数量（跨簇、只能一个方向、可重复用）；
   > `teleportTwoWay` = **双向传送门**数量（跨簇、可来回）
   >
   > `oneWayConsumable` = 「草盖地洞」的数量，**取值 1~3**（已确认）—— 既是**配额**（不是自由参数），也直接决定 D13 状态空间的大小（N × 2^k，k ≤ 3 → 完全可枚举）
2. **确定性**：同 spec + 同 seed → 同地图（**逐格比对**，不是"看起来一样"）
3. **可复用**：进关卡时若已有该关卡的地图（内存缓存，后续落盘）→ 直接复用；没有才生成
4. **配额必须可满足**：规格要求 5 个战斗格但只有 3 个可用格 → **明确报「规格不可满足」**，而不是塞个空的
5. **合法性由 D13 判定**：生成结果必须过 D13 校验（零告警）才算数

**生成流程（4 阶段）**

| 阶段 | 做什么 | 关键点 |
|---|---|---|
| 1 | **结构骨架**：生成 N 个**互不连通**的簇（每簇内部随机游走生长） | 每簇内部连通；任意两簇之间**无相邻格子对** |
| 2 | **放门 + 埋洞**：传送门连接不同簇（**≥ N-1 对**）；在簇内**割点**埋 1~3 个消耗型格（草盖地洞） | 簇图必须**连通**（把传送门当超边做 BFS 检查）。洞必须落在**割点**上（Tarjan 找割点），否则消耗后不会分裂；还要做**可满足性检查**：同一个洞不能被两条必需路径同时占用 |
| 3 | **簇内加边加环**：在每簇内部加非树边，让簇内路径丰富 | 避免簇内退化成一条直线（那样没有绕路余地，死锁风险高） |
| 3 | **配额填充**：把事件按配额填进非关键格 | 填充顺序与选点规则**必须固定**，否则破坏确定性 |
| 4 | **D13 校验 + 收敛** | 不合格 → 局部修正或换 seed 重试；**重试率是核心指标** |

**合法性收敛：构造式为主、校验兜底**

- **策略 B（构造式，主）**：先长树（保证连通）→ 再加边（只加在能到终点的格子上）→ **不需要重试**就能保证无软锁

### D12 · 地图簇结构（初始多簇 + 洞消耗再分裂） 🔺 **核心机制** **已完成** ✅
> **🔑 关键认知（主人 2026-10-20 两度澄清）**：地图的「簇」有**两个来源**：
>
> **① 初始就有多个簇** —— 靠**传送门**连接。传送门是**静态、可重复使用**的跨区通道，
> 所以初始地图可以是「几块分离的区块 + 传送门把它们连起来」（参考图 R-06 的「隧道」格）。
>
> **② 洞消耗后会再分裂** —— 两块区域只靠一个洞格子相连时，初始并不算分离（还有洞连着）；
> 玩家穿过那个洞、洞消失之后，两块区域才真的分开，**簇数 +1**（参考图 R-05/R-06 的黑色空隙就是被消耗掉的洞）。
>
> **所以完整的地图结构是四层的**：
> | 层 | 性质 | 边/节点 | 跨簇能力 |
> |---|---|---|---|
> | 格子层 | 普通移动 | 邻接**双向**边 | 簇内 |
> | **单向门层** | 跨区通道，**只能单向** | **永久有向边**（格子对，可重复用，但走不回头） | 单向跨簇 |
> | 双向传送层 | 跨区通道 | **永久双向超边**（格子对，静态可重复用） | 双向跨簇 |
> | 洞层 | 一次性 | **消耗型节点**（1~3 个，用掉即从地图删除） | 一次性跨簇 |
>
> ⚠️ **簇的划分规则（关键）**：把**洞节点**移除后，在「**邻接边 + 双向传送超边**」下的连通分量 = **簇**。
> **单向门不算连接边** —— 它是有向的，只提供单向通行 → **单向门两侧属于不同的簇**。
> 洞同理不算（它是消耗型的，用掉即断）。
>
> **生成器两件事都要做**：① 造出 N 个互不连通的簇，用传送门连起来（≥ 簇数-1 对）；
> ② 在簇内的割点埋 1~3 个洞，玩的过程中簇会再分裂。
>
> **难度：🔺 最高 → 高**（比"纯生成多簇"略低：不用设计复杂的簇形状算法——每个簇内部
> 随机游走生长即可，簇间靠**传送门**而不是靠"留空隙"来隔开）。
>
> ⚠️ 仍要**小步、可回退**——每阶段都有独立完成判据，每阶段结束都用 **D13 校验器**跑一遍。

**技术难点拆解（4 个各自独立的坑）**

| # | 难点 | 为什么会写错 | 对策 |
|---|---|---|---|
| 1 | **簇必须真的互不连通** | 簇间靠传送门连，所以「不连通」指的是**没有格子路径**；若簇间还残留相邻格子，玩家就能直接走过去，传送门形同虚设 | 生成后统一「剔除与已生成簇相邻的格子」，并断言「任意两簇之间不存在相邻格子对」 |
| 2 | **传送门数量必须够** | N 个簇需要 ≥ **N-1** 对传送门才能保证簇图连通，少一对就有簇永远到不了 | 生成后做**簇图连通性检查**（把传送门当超边做 BFS），不连通就补门或重生成 |
| 3 | **洞必须落在割点上** | 洞若在环上（两侧另有通路），消耗后只少一格，**地图不会分裂** → 做了等于没做 | 生成时用 Tarjan 找全部割点，洞只从割点里选；D13 的簇图分析正好能验 |
| 4 | **分裂后传送门两端可能落到不同新簇** | 传送是**跨空间**的，两端即使本地分裂了仍然能互通；但**簇的划分必须把传送门算作连接边**，否则会误判「不可达」 | D13 里缩簇时把传送门并入连通性计算（见 D13 注意事项） |
| 5 | **单向门必须跨簇且方向正确** | 单向门只在一个方向可走。放在同一簇内毫无意义；方向反了（指向来路）玩家会直接卡死 | 生成后校验：单向门两端属于**不同簇**，且方向是"离开当前簇"而非指回来路 |

**为什么簇要造出「窄口」**

单纯用「随机游走」长出来的簇**内部全是环，一个割点都没有** ——
洞放上去消耗掉也**不会**让簇分裂（等于白做）。
所以 `ClusterBuilder` 显式造出窄口：
**两块子区域之间只有窄口一个连接** → 窄口是割点 → 洞放上去 → 消耗后这一簇真的裂成两块。

**「洞」的口径终于统一（这次踩得最深）**

| 场景 | 洞算不算连接边 | 为什么 |
|---|---|---|
| 判定「洞是不是割点」 | **算**（洞是普通可走格） | 问的是「洞**还在**的时候，它是不是连接两块的关键」 |
| D13 簇图分析 | **不算**（洞是消耗型节点） | 问的是「洞**已消耗**之后，地图怎么连」 |

一开始用 D13 的簇图分析判割点 → 它会把**所有洞**都移除 → 「移除洞前后没区别」→ **永远判不出割点**。

**与原计划的偏差（诚实记录）**

1. **簇数用 2 而不是 3**。121 格的网格里塞 3 块互不相邻的区域（还要留隔离带）长不开，
   2 块（各约 30 格）稳定。`spec.clusters` 是数据，改成 3 随时可用。
2. **「移除所有洞后仍要能到 BOSS」这条旧规则在簇模式下跳过了** ——
   它与新模型直接冲突（新模型里洞**就是**唯一连接，移除它本来就该断开）。
   合法性改由 D13 校验器兜底（它的状态空间搜索会判断「有没有能通关的走法」）。
3. **「簇」有两个口径，本文档明确区分**：
   - **几何簇**（D12 用）：按**邻接边**算的连通分量 = 视觉上分离的区块（参考图 R-05/R-06）
   - **D13 的簇**：按「邻接 + 双向传送超边」算的连通分量 = 连通性分析用的概念
   两者不一定相等（双向传送门会把两个几何簇连成一个 D13 簇）。
