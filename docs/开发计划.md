## 1. 三步工作流

每个条目都必须走完这三步才算完成，跳步即视为未完成。

### 第 1 步 · 需求

**输入**：主人的指示 + 参考图编号。

**我要产出**（缺一项就动手 = 耍赖）：

1. **做什么** —— 一句话说明改哪个界面 / 哪个文件
2. **长什么样** —— 元素清单、参考图编号、要填的数值
3. **验收点** —— 什么现象算做完了，能被截图或日志证明

**准入**：条目三要素齐了才进开发。
**准出**：主人认可需求表述。对参考图的解读有歧义时，先复述一遍再动手。

> 🔺 **难度最高**（D12 地图多簇生成）与 🔺 **重要度核心**（D13 地图校验器）额外要求：动手前先出一版**分阶段方案**给主人过目，确认「回退路径」成立后再写第一行代码。

### 第 2 步 · 开发

**顺序**（铁律见 `.trae/rules/project_rules.md`）：

0. **动代码前先查 [`docs/踩坑记录.md`](踩坑记录.md)** 有没有同类坑。本项目 UI 的三个高频坑：
   §8 根节点漏绑 script、§10 子节点也要挂脚本且一个 .cs 只能一个类、§11 事件驱动的初值要手动推一次。
1. 布局写进 `.tscn`（UI 优先建独立场景，禁止代码硬编码坐标）
2. 逻辑写进 `.cs`（一个 `.cs` 只挂一个类，根节点和槽位节点都要挂）
3. 事件回调**首行** `GD.Print($"[类名] 方法名 called")`、**末行** `... completed`
4. 挂进父场景 / 接到现有管理器上

**准出**：`dotnet build` 0 错。新增 `.tscn` 引用的资源必须真实存在。

### 第 3 步 · 验证

**我做**（后台跑，不抢主人鼠标）：

- 用 `Scenes/Dev/DevScenario.tscn` + 预设进场景，`background: true`
- **主动把关键截图和日志原文贴进聊天**，不只汇报「通过了」
- 断言按条目里的「验证」栏执行

**主人做**（通过后）：

- 我开**可见模式**的调试场景准备器窗口，主人自己点、自己验证、**自己关**，我不 stop
- 主人反馈后我改，改完重跑第 3 步

**准出**：截图证据 + 主人确认。**没贴截图就不算验证过。**

**四种验证形态**（每个条目的「验证」栏必须指明用哪几种）：

| 形态 | 含义 |
| :--- | :--- |
| 视觉 | 截图与参考图对照，看布局/配色/层级对不对 |
| 行为 | 点哪里 → 发生什么，是否符合预期 |
| 数据 | 日志里的具体数值（如 `携带地图血量进入战斗: 125/125`） |

## 4. 逐项展开

> 📌 下面各章节按 **ID 编号**排列，**执行顺序看 §3 总表**（总表已按「重要度 ÷ 难度」重排）。

### D13 · 地图可达性与死锁校验（通用算法模块） 🔺 **最高优先 · 可移植** ⬜

**为什么它排第一**

- 主人指出：关卡可以是**人工配置**的，那么真正必需的不是"随机生成"，而是**"校验"**——有没有走过去了回不来、有没有通不了关。
- 这套东西本质是**有向图可达性 + 死锁检测**。换个邻接函数就能用在方形网格、卡牌爬塔的房间图、任何"格子 + 传送"结构上 → **能直接带到别的项目**。
- 它是**后续一切地图改动的安全网**：D5（阴影）、D12（多簇）、将来的人工关卡编辑，全靠它兜底。先有网，再动刀。

**需求**

一个**独立、可移植**的校验模块：输入「节点 + 有向边 + 关键节点集」，输出**结构化诊断报告**（不是 bool）。至少能检出这 6 类问题：

| # | 问题 | 玩家感受 | 判定方式 |
|---|---|---|---|
| 1 | **通不了关** | 玩到一半发现走不到 BOSS | 起点 → 终点在有向图上不可达 |
| 2 | **走过去了回不来（软锁）** | 踩进某个格子后再也出不去 | 存在格子 x：x 从起点可达，但 x → 终点**不可达** |
| 3 | **不可达区域** | 地图上有一大片永远去不了 | 存在不在「起点可达集」里的格子 |
| 4 | **关键格不可达** | 必经事件/商店/BOSS 被隔断 | required 节点 ∉ 可达集 |
| 5 | **死路** | 进去才发现是死胡同 | 出度为 1，且唯一出边是**单向**传送 |
| 6 | **孤岛 / 多簇** | 有一块区域跟主线完全断开 | 全图弱连通分量数 > 1 |

报告必须**逐条列出问题格子**（坐标 + 类型 + 原因），不能只说"有问题"。

**建模：传送是有向边** ← 这是整个算法成立的关键

| 移动方式 | 图上的边 |
|---|---|
| 邻接移动（六边形相邻格） | 双向边 |
| **单向传送** | **1 条有向边**（走过去就回不来） |
| 双向传送 | 2 条有向边 |

于是"走过去了回不来"**自动变成有向图上的可达性问题**，不需要任何特判——这是把传送当有向边建模换来的干净。

**算法**（两次 BFS 就够）

1. 建图：节点 = 格子，有向边 = 邻接 + 传送
2. **正向 BFS**（从起点）→ 可达集 **R**
3. **反向 BFS**（从终点）→ "还能到终点"的集合 **T**
   - ⟹ 格子 x ∈ **R \ T** ⟹ **走进 x 就通关无望**（软锁区）——这就是第 2 类问题
4. 关键格校验：required ⊆ R，且到它的路径上不强制经过单向传送
5. 死路：出度 = 1 且唯一出边是单向传送
6. 孤岛：全图弱连通分量数
7. 输出报告：问题类型 + 坐标 + 建议

**开发**

- 新建 `Scripts/MapValidation/`——**独立模块，不掺 HexMap 细节**
  - `IMapGraph.cs` —— 抽象图接口：`NodeCount` / `GetOutgoingEdges(node)` / `GetNodeLabel(node)`
  - `MapValidator.cs` —— 纯算法（两次 BFS + 集合运算），**不引用任何 Godot 类型**
  - `MapValidationReport.cs` —— 结构化报告（问题列表 + 统计）
  - `HexMapGraph.cs` —— 适配器，把 `HexMap` 包装成 `IMapGraph`（六边形版本）
- 算法层只用 `int` 节点 id + 边集合 → **整目录可直接拷到其他项目**
- 接入点：
  - `HexMapGenerator.Generate()` 末尾**立刻自检**，不通过就重新生成（沿用现有 `Verify*` + 递归重生成的模式）
  - 人工关卡加载时同样自检
- 配套：`Data/maps/` 放人工关卡（后续条目，可选）

**验证**

- 数据：**构造已知有问题的地图做反向用例**——
  - 单向传送指向死胡同 → 必须报「软锁」
  - BOSS 被单向传送隔断 → 必须报「通不了关」
  - 一个完全孤立的岛 → 必须报「不可达区域」
  - 正常地图 → 必须**零告警**
- 行为：随机地图跑 1000 次，统计问题率（应趋近 0）
- 回归：现有 8 个调试预设全通；现有 `Verify*` 可被新校验器取代或并存
- **可移植性**：把 `Scripts/MapValidation/` 单独拷到一个空目录，喂一个 3 节点的玩具图，确认**不需要 Godot 就能跑**——这一条直接证明它能带走

### D12 · 地图多簇生成（互不连通的区块） 🔺 **最高难度 · 核心难点** ⬜

> **为什么是最高难度**：这条要同时重写地图生成算法、**重新定义「可达性」的含义**、并把传送系统从「随机装饰」改造成「跨区主干道」。这类算法很多 AI 都写不对——典型翻车是生成出一整块（等于没改），或者生成出走不到终点的孤岛。
>
> **为什么排到最后（重要度只有中等）**：关卡可以**人工配置**，多簇生成是"锦上添花"而不是必需品；而且等 **D13 校验器**就位后，多簇生成可以**边生成边自检**，不必再盲改 970 行。**难度最高 + 重要度中等 = 性价比最低**，所以放最后一个单独攻——等前面的地基都齐了、地基齐了它反而最好做。
>
> ⚠️ 做法上仍然要**小步、可回退**——见下方「分阶段实施」，每阶段都有独立完成判据；每阶段结束都用 **D13 校验器**跑一遍，不通过就退回去。

**技术难点拆解（4 个各自独立的坑）**

| # | 难点 | 为什么会写错 | 对策 |
|---|---|---|---|
| 1 | **簇与簇必须真的不相邻** | 随机放簇很容易两个簇贴到一起，或中间只隔一个格子、视觉上像连着 | 生成后统一「剔除与已生成簇相邻的格子」，再做硬断言校验 |
| 2 | **起终点必须落在不同簇** | 现有 `FindFarthestTile` 会在同一簇里找最远格 → 起点终点同簇 = 多簇白做 | 终点改为「在跨簇可达域内取最远」，并断言 start/end 不同簇 |
| 3 | **「可达」的定义变了** | `IsReachable` / `FindShortestPath` 只走邻接 BFS，跨簇必然判为不可达 | 邻接 + 双向传送边 = **多模式可达**，两处实现都要改 |
| 4 | **事件与传送要重新定位** | 现有事件放置基于「完整网格 + criticalSet」，簇化后可能落到**不存在的坐标**上 | 事件只在簇内放；传送改为跨簇成对放置，数量 ≥ 簇数 - 1 |

**分阶段实施（每阶段都是可回退点）**

| 阶段 | 做什么 | 完成判据 |
|---|---|---|
| 0 | 加配置开关，保留旧的单簇生成路径 | 开关切回旧路径，行为与现在**完全一致** |
| 1 | `GenerateIslandClusters`：产出 2~4 个互不相邻的簇 | 断言「任意两簇之间无相邻格子对」通过 |
| 2 | 多模式可达性（邻接 + 传送边） | 起终点分处两簇时 `IsReachable` 为真 |
| 3 | 跨簇成对放置传送 + 事件只在簇内放 | 走到隧道能传到另一簇，并继续走向 BOSS |
| 4 | 回归：4 个调试预设 + 地图存档 | 全部跑通，状态恢复无异常 |

> 💡 **降低风险的关键**：`HexMapGenerator` 与 `HexCoord` **不依赖任何场景树节点**（无 `GetNode` / `GetTree` / `owner`，`HexCoord` 是纯 struct）。所以阶段 1~3 的断言可以在 **Godot 无头模式**（`--headless`）下批量跑，不必每次开窗口肉眼看。这把"盲改 970 行"变成了"可断言的纯算法改造"。
>
> 🔗 **依赖 D13**：本条开工前 **D13 校验器必须先就位**。阶段 1~3 每一步都用它自检（软锁 / 通不了关 / 不可达区域三类必须全清），否则等于盲改。

**需求**
- 地图由 **2~4 个互不相连的区块簇**组成。簇与簇之间**不生成中间格子**——是结构上不连通，不是"格子存在但走不进去"。
- 簇内连通；**起点在簇 A，终点（👹 BOSS）必须在另一个簇**。
- 跨簇**必须**经由双向传送（隧道）格子。项目已有 `HexEventType.TeleportTwoWay` + `TeleportDialog`，**不新造机制**。
- 簇数与隧道对数绑定：**簇数 ≤ 隧道对数 + 1**，否则必然有簇永远走不到。
- 洞穴 / 沼泽 / 战斗 / 商店等事件只放在簇内。
- 参考 R-05 / R-06（几块分离的六边形区域，中间是黑色空白）。
- 关联 `tasks.md` 1.6。

**现状（改之前是什么样）**
- `HexMapGenerator.GenerateHexGrid(radius)` 生成**完整矩形网格**（`(2r+1)²` 全部存在），底层网格天然全连通。
- 唯一的"断开"手段是 `PlaceHoleTiles` 打的**洞穴**格子（`CanEnter=false`）——那是"格子在、走不进去"，不是结构断开。
- `PlaceTwoWayTeleportTiles` 是在整张网格上**随机**挑两个空格配成一对，位置与"跨区"毫无关系。
- `HexMap.IsReachable` / `FindShortestPath` 只走**邻接** BFS；`EnsurePathConnectivity` / `VerifyAllHolesPlacement` 基于此判定起终点可达。

**开发**
1. `HexMapGenerator.GenerateHexGrid(radius)` → `GenerateIslandClusters(...)`
   - 决定簇数 N（难度配置给出，建议 2~4）
   - 每簇：随机中心 + 随机形状（圆形 / 椭圆 / 不规则轮廓 / 随机游走生长）
   - **簇间至少留 1 圈空隙**：生成后剔除与已生成簇相邻的格子，保证「任意两簇之间不存在相邻格子对」
2. 起点改为在**簇 A 的边缘**取；终点在**跨簇可达域**里取最远格（BOSS 必须落在与起点不同的簇）
3. `HexMap.IsReachable` / `FindShortestPath` 扩展为**多模式可达**（邻接 + 双向传送边）；或在生成器内维护「簇图 + 传送对」做连通性判定
4. `PlaceTwoWayTeleportTiles` 改为**跨簇成对放置**：一端在簇 X 边缘、一端在簇 Y 边缘，数量 ≥ 簇数 - 1
5. `EnsurePathConnectivity` / `VerifyAllHolesPlacement` 适配多簇语义
6. `PlaceRandomEvents` / `PlaceSwampTiles` / `PlaceHoleTiles` 确认不会落到不存在的坐标
7. **风险控制**：`HexMapGenerator.cs` 已 970 行、`Generate` 串了 15 步。**先加配置开关**（数据驱动，风格同 `Data/enemies.json`），保留旧的单簇生成作为回退路径
8. 移动侧：`HexMapController` 的"只接受相邻格子点击"限制不能挡住跨簇传送——传送走事件，不是相邻移动

**验证**
- 数据：日志打印簇数、每簇格子数、每对簇的最短间隔；断言「任意两簇之间无相邻格子对」
- 视觉：截图对照 R-05 / R-06
- 行为：起点在簇 A → 走到隧道 → 传送到簇 B → 能走到 BOSS 并触发 BOSS 战
- 回归：`default` / `near_boss` / `step_on_boss` / `boss_battle` 四个预设仍跑通；`near_shop` 的落点仍能落在商店旁边
